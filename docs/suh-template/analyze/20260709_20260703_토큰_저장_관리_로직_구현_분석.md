### 📊 분석 요약

**감지된 프로젝트 타입**: Flutter (`pubspec.yaml` + `lib/`)
**주요 기술 스택**: Dart SDK `^3.9.2`, `dio: ^5.8.0`, `flutter_secure_storage: ^9.2.4`, 상태관리 패키지 없음(순수 StatefulWidget)
**코드 스타일**: 파일명 snake_case, `feature-first`(`lib/features/*`) + 공용 인프라는 `lib/core/*`·`lib/data/*` 분리, static 메서드 위주 API 클래스(`AuthApi`), private 생성자로 유틸 클래스 인스턴스화 차단(`const AppSecrets._()` 패턴), 한글 doc 주석

관련 선행 문서: `docs/suh-template/plan/20260709_20260703_토큰_저장_관리_로직_설계.md`

### 🔍 현재 상태

**인증/토큰 관련 파일 전수**:

| 파일 | 역할 | 문제 |
|---|---|---|
| `lib/core/network/dio_client.dart` | Dio 싱글톤, `FlutterSecureStorage` 인스턴스를 생성자 내부에서 `const`로 생성해 `AuthInterceptor`에만 주입 | storage가 캡슐화되어 화면 코드에서 접근 불가 |
| `lib/core/network/interceptors/auth_interceptor.dart` | 요청마다 accessToken 읽어 헤더 부착, 401 시 refreshToken으로 갱신 | 자체적으로는 정상 동작하지만 애초에 storage에 값이 들어올 방법이 없음 |
| `lib/data/remote/auth_api.dart` | `signUp`/`login`/`getRefreshToken`/`logout` API 호출, `TokenResponse`/`OAuthLoginResponse` 반환 | 반환만 할 뿐 저장 책임 없음 (설계상 맞음) |
| `lib/features/auth/presentation/signup_screen.dart:_onSignupTap` | `await AuthApi.signUp(...)` 호출 후 반환값 버림, 바로 `HomeScreen`으로 이동 | **토큰 저장 호출 누락** |
| `lib/features/auth/presentation/login_screen.dart:_handleLoginResponse` | `response.tokens != null`이면 `HomeScreen`으로 이동만 함 | **토큰 저장 호출 누락** |
| `lib/features/splash/screens/splash_screen.dart` | 헬스체크 후 무조건 `LoginScreen`으로 이동 | 자동 로그인 없음 (이번 범위 아님, 후속 작업) |
| `lib/app/app_startup.dart` | `KakaoSdk.init` → `GoogleSignIn.initialize` → `DioClient.init(onUnauthorized:)` 순서로 앱 부팅 시 1회 초기화 | `onUnauthorized` 콜백 등록 지점 — 현재 아무도 콜백을 넘기지 않아 no-op |

**핵심 결함**: `AuthInterceptor`가 읽는 `FlutterSecureStorage`와 로그인/회원가입 화면이 받는 `TokenResponse`가 서로 연결되어 있지 않음. 즉 "발급"과 "저장" 사이에 배선이 빠져 있음 — 계획 문서에서 확인한 문제가 코드 레벨에서도 정확히 일치함.

**의존성/통합 지점**:
- `DioClient._instance` (static 싱글톤) → `AppStartup.initialize()`에서 `main.dart` 부팅 시 1회 생성.
- `AuthInterceptor`는 생성자 주입(`storage`, `dio`, `onUnauthorized`)만 받고 다른 전역 상태 참조 없음 — 새 `TokenStorage`로 교체해도 인터셉터 내부 로직(401 재시도, 동시 refresh 방지 `Completer`)은 그대로 재사용 가능.
- `OAuthLoginResponse.tokens`는 `TokenResponse?` (nullable, 미가입 시 null), `TokenResponse`(signup)는 non-null 필드 — 저장 호출 지점에서 이 차이를 그대로 다뤄야 함.

### 🎯 구현 목표

계획 문서에서 확정한 범위 그대로:
1. `TokenStorage` 공용 서비스 신설 — `flutter_secure_storage`를 감싸고 read/write/clear + 로그인 상태 `ValueNotifier<bool>` 노출.
2. `DioClient`/`AuthInterceptor`가 이 `TokenStorage`를 통해 동작하도록 배선 교체 (동작 자체는 기존과 동일하게 유지).
3. `LoginScreen`/`SignupScreen`이 토큰 발급 응답을 받는 즉시 `TokenStorage`에 명시적으로 저장.
4. 로그아웃 UI, 스플래시 자동 로그인 라우팅은 **이번 구현에서 제외**.

### ⚠️ 주의사항

- **싱글톤 초기화 순서**: `TokenStorage.instance`는 lazy singleton으로 만들면 `DioClient`처럼 초기화 순서 문제가 없지만, `DioClient._()` 생성자 시점에 `TokenStorage.instance`를 먼저 참조하게 되므로 순환 생성 문제는 없는지 확인 (TokenStorage는 DioClient를 참조하지 않으므로 안전함).
- **`TokenResponse.empty()` 폴백 값 저장 방지**: `AuthApi.signUp`/`AuthApi.login`은 `response.data`가 없을 때 빈 문자열 토큰(`TokenResponse.empty()`)을 반환한다. 화면에서 무조건 `saveTokens`를 호출하면 빈 문자열이 저장되어 이후 "빈 토큰으로 Authorization 헤더가 붙는" 이상 상태가 생길 수 있음 — 저장 전 accessToken이 비어있지 않은지 검증 필요.
- **테스트 인프라 부재**: `flutter_secure_storage`는 플랫폼 채널 기반이라 순수 `flutter test`에서 바로 동작하지 않음. `TokenStorage`를 만들 때부터 내부 `FlutterSecureStorage` 인스턴스를 생성자 파라미터로 받을 수 있게 설계해두면(기본값은 실제 인스턴스), 테스트에서 `FlutterSecureStorage`를 대체할 방법을 별도로 고민하거나 `TokenStorage` 자체를 추상화(interface)해 fake 구현을 주입하는 방식을 implement 단계에서 결정해야 함.
- **기존 401 동시 요청 처리 로직 보존**: `AuthInterceptor`의 `_isRefreshing`/`_refreshCompleter` 동시성 제어는 `TokenStorage`로 교체해도 그대로 유지해야 함 — 리팩토링 중 실수로 단순화하면 다중 요청 401 시 refresh가 중복 호출될 수 있음.
- **범위 외 항목 재확인**: 스플래시 자동 로그인, 로그아웃 버튼/`AuthApi.logout` 연결은 이번 구현 계획에 포함하지 않음 — `TokenStorage.isLoggedIn` ValueNotifier는 이번에 "노출"만 하고 실제 구독/라우팅 연결은 후속 작업.
