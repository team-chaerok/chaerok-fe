작업 브랜치: `20260729_#41_기능추가_관광지_조회_코스_추천_지역별_필름롤_구현` (base: `~/Project/chaerok-fe` main worktree)

## 📊 분석 요약

- **프로젝트 타입**: Flutter (단일 앱, `chaerok-fe`) — **프론트엔드 전용 저장소**. 백엔드 Entity/DB는 별도 저장소 소관이라 이 저장소에서 직접 확인/변경 불가.
- **상태관리**: Provider/Riverpod/Bloc 등 라이브러리 없음. `StatefulWidget` + `setState` 패턴만 사용 (pubspec에 상태관리 패키지 미포함).
- **네트워킹**: `DioClient` 싱글톤 + `AuthInterceptor`/`ErrorInterceptor`/`LoggingInterceptor`. 공통 응답은 `ApiResponse<T>`, 공통 예외는 `ApiError`(statusCode/message/errorCode) + `apiErrorMessage()` 헬퍼.
- **구조**: `lib/core`(공용) · `lib/data`(models/remote) · `lib/features/{feature}/data|presentation` · `lib/shared/widgets` — feature-first + layer-first 혼합.

## 🔍 현재 상태 (중요 발견)

### 1) 이미 백엔드에 구현되어 있고 FE 클라이언트까지 만들어졌지만 **화면에서 전혀 사용되지 않는** API가 다수 있음

| API | 클라이언트 | 사용처 |
|---|---|---|
| `POST /api/regions/resolve` | `RegionsApi.resolveRegion` | ✅ `LocationVerificationScreen`에서 사용 중 |
| `GET /api/places/external` | `PlacesApi.getExternalPlaces` | ✅ `LocationVerificationScreen`에서 사용 중 |
| `GET /api/places` | `PlacesApi.getPlaces` | ❌ 미사용 (정의만 존재) |
| `GET /api/places/{id}` | `PlacesApi.getPlaceDetail` | ❌ 미사용 |
| `GET /api/places/search` | `PlacesApi.searchPlaces` | ❌ 미사용 |
| `POST /api/courses` | `CoursesApi.createCourse` | ❌ 미사용 |
| `POST /api/courses/active/places` | `CoursesApi.addActiveCoursePlaces` | ❌ 미사용 |
| `GET /api/courses/recommend` | `CoursesApi.getRecommendedCourses` | ❌ 미사용 |
| `GET /api/courses/active` | `CoursesApi.getActiveCourse` | ❌ 미사용 |

즉 이번 이슈의 핵심은 **"백엔드 API를 새로 만드는 것"이 아니라 "이미 계약된 API를 화면에 연결하는 것"**에 가깝다. (단, 백엔드가 실제 스테이징/개발 서버에서 정상 동작하는지는 별도 검증 필요 — FE 저장소만으로는 확인 불가.)

### 2) "필름롤(FilmRoll)" 개념은 프론트엔드 어디에도 없음 — 대신 **Course가 그 역할을 이미 겸하고 있음**

- `SelectedCourseResponse`: `courseId, regionId, title, status(문자열), placeCount, completed(bool), places[]`
- `CoursesApi.createCourse`: "사용자가 선택한 장소로 **ACTIVE** 코스 생성 — 기존 ACTIVE 코스가 있으면 INACTIVE 처리하고 새로 생성" (주석 원문)
- `CoursesApi.addActiveCoursePlaces`: "ACTIVE 코스는 최대 **3개** 장소까지만 저장 가능" (주석 원문)
- `CoursesApi.getActiveCourse`: 로그인 사용자의 현재 ACTIVE 코스 단건 조회

→ 사용자당 "진행 중 코스는 지역 불문 1개"라는 ACTIVE/INACTIVE 모델이 이미 백엔드에 있고, 지역별로 여러 개를 동시에 들고 있는 구조가 아님. 원 스펙의 "필름롤(지역별 진행 단위)"과 "코스(장소 조합)"를 분리하는 2계층 설계가 아니라, **Course 자체가 1계층으로 두 역할을 합쳐 담당**하고 있다.
→ 장소 개수 제약도 스펙의 "최소 2~최대 6개"가 아니라 **최대 3개**로 이미 고정되어 있다.

**결론**: 새 `FilmRoll` 엔티티/화면을 만드는 대신, 기존 `Course`/`ACTIVE 코스` 모델을 그대로 필름롤 역할로 사용하는 것을 권장한다 (백엔드가 이미 이렇게 계약되어 있고, 이 저장소에서 백엔드를 바꿀 수 없으므로). 사용자가 원 스펙에 준 규칙(최소2/최대6, 지역별 여러 개 필름롤 등)은 실제 계약과 다르며, 이 저장소 범위에서는 **기존 백엔드 계약을 우선**한다.

### 3) 지원 지역 판별은 클라이언트 enum이 아니라 **서버 응답 플래그** 기반

- 지원 지역 4개(GONGJU/BUYEO/SEOSAN/YESAN) 같은 코드/enum이 FE에 없음.
- 서버가 `provinceName`+`cityCountyName`을 받아 `RegionResponse{ serviceArea: bool, regionId, provinceName, cityCountyName }`로 응답 — **미지원 지역도 예외가 아니라 200 + `serviceArea: false`**로 내려온다.
- 지역 표시명(`cityCountyName`), 대표 좌표, TourAPI 코드 등은 전부 서버가 들고 있고 FE는 `regionId`(int, opaque)만 넘겨 다른 API를 호출.
- → 원 스펙의 `SupportedRegion` enum / `RegionNormalizer` / `SupportedRegionPolicy`는 **서버 책임**이며, FE에 새로 만들 필요가 없다(만들면 서버와 이중 관리가 되어 오히려 불일치 위험).

### 4) 위치 인증 흐름 (`LocationVerificationScreen`)

```
세션 캐시 확인 → 위치 권한 확인/요청 → 좌표 획득(Geolocator)
→ Kakao Local API로 좌표→행정구역 변환(KakaoLocalApiService)
→ provinceName == '충청남도' 아니면 (디버그 모드 제외) outOfServiceArea
→ RegionsApi.resolveRegion → serviceArea false면 outOfServiceArea
→ PlacesApi.getExternalPlaces(regionId) → 성공 시 LocationVerificationResult 반환/세션 캐시
```

- **디버그 전용 임시 목업이 이미 존재**: `kDebugMode`이고 서비스 지역 밖일 때, 좌표는 실제 값을 유지한 채 백엔드로 보내는 지역명만 `충청남도 공주시`로 하드코딩 치환 (`_debugFallbackProvinceName/_debugFallbackCityCountyName`). 지역을 골라 테스트하는 정식 mock 기능은 아님.
- `HomeScreen`은 세션 캐시가 없으면 `LocationVerificationScreen`을 push하고, 결과를 `kDebugMode`에서만 디버그 카드로 보여줄 뿐 실제 기능(코스/필름롤)과는 연결돼 있지 않음 (코드 주석에도 "이번 작업 범위 밖"이라고 명시돼 있음 — 이번 이슈가 바로 그 범위임).

### 5) 공통 예외 구조

- `ApiError{ statusCode, message, errorCode? }`, `apiErrorMessage(Object)`로 UI에 문자열만 뽑아 쓰는 패턴.
- `errorCode`로 분기하는 클라이언트 로직은 현재 어디에도 없음(전부 `message` 그대로 표시). 원 스펙의 `UNSUPPORTED_REGION` 같은 에러코드 목록은 실제로는 사용되지 않고 `serviceArea` boolean으로 대체되어 있으므로, 새 기능도 이 패턴(코드 분기보다 응답 필드/메시지 표시 위주)을 따르는 게 일관적이다.

## 🗄️ DB / 백엔드 변경 필요 여부

**이 저장소 범위에서는 없음.** `chaerok-fe`는 프론트엔드 전용이며 필요한 API(`/api/places*`, `/api/courses*`, `/api/regions/resolve`)가 이미 계약되어 있고 FE 클라이언트도 이미 존재한다. 백엔드 신규 개발이 필요한 항목은 이번 분석에서 발견되지 않았다. 다만:
- 실제 개발/스테이징 서버에서 각 API가 명세대로 동작하는지는 FE 저장소만으로 검증 불가 — 연동 중 실제 응답과 DTO가 어긋나면 그때 백엔드팀과 별도 협의 필요.
- "지역별 대표 이미지" 같은 순수 표시용 리소스가 서버 응답에 없다면 그건 DB 변경이 아니라 FE 자체 정적 리소스로 처리 가능.

## ⚠️ 주의사항 / 원 스펙과의 차이 (사전 확인 필요)

원 요청 스펙은 이 저장소에 없는 백엔드 설계(FilmRoll 별도 엔티티, 장소 2~6개, `UNSUPPORTED_REGION` 예외 코드, `SupportedRegion` enum 등)를 가정하고 있었으나, 실제로는:

| 스펙 가정 | 실제 확인된 구조 |
|---|---|
| FilmRoll(지역별 진행 단위) + Course(장소 조합) 2계층 | Course 1개가 ACTIVE/INACTIVE로 필름롤 역할까지 겸함 |
| 장소 최소 2 ~ 최대 6개 | 최대 3개 (API 주석 기준) |
| 지역당 필름롤 여러 개(완료 후 재생성) 가능 | ACTIVE 코스는 사용자당 1개, 새로 만들면 기존 것 INACTIVE 처리 |
| `UNSUPPORTED_REGION` 등 예외 코드 체계 | `serviceArea: boolean` 응답 필드로 판별 (예외 아님) |
| `SupportedRegion`/`RegionNormalizer` 클라이언트 enum | 서버가 `regionId`/`serviceArea`로 이미 처리, 클라이언트 enum 불필요 |

→ **이번 구현은 실제 백엔드 계약(Course/ACTIVE/최대 3개/serviceArea)을 기준으로 진행**하는 것을 권장합니다. FilmRoll을 별도로 만들고 싶다면 이는 백엔드 신규 개발이 필요한 별도 이슈(다른 저장소)로 분리해야 합니다.
