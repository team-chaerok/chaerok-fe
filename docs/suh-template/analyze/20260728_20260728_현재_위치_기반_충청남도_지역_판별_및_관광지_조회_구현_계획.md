### 📊 분석 요약

**감지된 프로젝트 타입**: Flutter 모바일 앱 (Android/iOS/macOS), 백엔드는 별도 리포지토리(`chaerok-be`)
**주요 기술 스택**: Flutter 3.9, `dio`(HTTP), `geolocator`+`permission_handler`(위치), `kakao_flutter_sdk_user`/`google_sign_in`(OAuth), `flutter_secure_storage`(토큰)
**코드 스타일**: 상태관리 라이브러리 없이 `StatefulWidget`+`setState`와 static 서비스/API 클래스(`XxxApi`, `XxxService`) 조합만 사용하는 단순 계층 구조. `data/`(서비스·API) / `presentation/`(화면) 분리 컨벤션(`features/<도메인>/data`, `features/<도메인>/presentation`).

이 문서는 `/plan`에서 작성한 [전략 문서](../plan/20260728_20260728_현재_위치_기반_충청남도_지역_판별_및_관광지_조회.md)를 기준으로 실제 구현 착수를 위한 파일 단위 계획을 정리한다.

## 🔍 현재 상태

### 이미 구현되어 있는 부분
- `lib/features/location/data/location_permission_service.dart`: 권한 상태 조회(`checkStatus`)/요청(`requestPermission`)/좌표 조회(`getCurrentPosition`)/설정 이동(`openSettings`) — macOS는 Geolocator 자체 권한 API로 폴백 처리됨. **변경 불필요, 그대로 재사용.**
- `lib/features/location/presentation/location_permission_mockup_screen.dart`: 권한 상태별(승인/거부/영구거부) UI 분기만 있는 QA용 Mockup. 실제 지역 판별·관광지 조회 로직은 없음.
- `lib/data/models/resolve_region_request.dart` / `region_response.dart`: 필드 정의만 있고 실사용처(API 클래스, `grep` 0건) 없음.
- `lib/data/remote/places_api.dart`: `getPlaces`(regionId), `getPlaceDetail`, `searchPlaces`, `getExternalPlaces`(regionId) 4개 메서드. 좌표 기반 반경 조회 메서드 없음.
- Android(`ACCESS_FINE_LOCATION`/`ACCESS_COARSE_LOCATION`), iOS(`NSLocationWhenInUseUsageDescription`) 위치 권한 선언은 #30 작업에서 이미 완료됨. **플랫폼 설정 변경 불필요.**
- `lib/features/settings/presentation/settings_screen.dart`에 `_onLocationPermissionMockupTap` QA 진입점이 있고, 코드 주석에 "실제 디자인 확정 후 정식 화면으로 교체되면 이 진입점은 제거할 것"이라고 명시되어 있음.
- `lib/features/home/presentation/home_screen.dart`: `initState`에서 `UsersApi.getMyInformation()`만 호출. 위치 관련 로직 없음.
- `lib/app/app.dart` → `SplashScreen`(`lib/features/splash/screens/splash_screen.dart`)이 헬스체크+세션 복원 후 `HomeScreen` 또는 `LoginScreen`으로 `pushReplacement`. 별도 라우터/네임드 라우트 없음.

### 네트워크 계층
- `DioClient`(`lib/core/network/dio_client.dart`)는 싱글톤이며 `baseUrl = AppSecrets.baseUrl`(채록 백엔드) 고정, `AuthInterceptor`+`ErrorInterceptor` 적용. 모든 실패는 `ErrorInterceptor`가 `ApiError`로 정규화하여 `DioException.error`에 담아 rethrow함 → 화면단에서는 `apiErrorMessage(e)`(`lib/data/models/api_error.dart`)로 사용자 메시지를 뽑아 쓰는 패턴이 `settings_screen.dart`/`home_screen.dart`에서 이미 사용 중.
- Kakao Local API(`dapi.kakao.com`)는 채록 백엔드가 아닌 외부 호스트이므로 `DioClient.instance`를 쓸 수 없음. `splash_screen.dart`의 `TokenStorage.instance.resolveSession(Dio(BaseOptions(...)))` 사례처럼, 이 프로젝트는 이미 "baseUrl이 다른 별도 `Dio` 인스턴스를 그때그때 생성"하는 패턴을 쓰고 있어 이번에도 동일하게 적용 가능.
- `AppSecrets`(`lib/core/config/app_secrets.dart`, 커밋 대상 아님)와 `.example` 파일 2종(`app_secrets.example.dart`, `app_secrets.dart.example`)이 함께 존재 — 3개 파일 모두 동일 필드로 갱신해야 함.

### 시크릿/설정 관리
- `kakaoNativeAppKey`(로그인 SDK용)만 존재. Kakao Local API용 REST API 키는 카카오 개발자 콘솔에서 별도 발급이 필요하며 아직 코드에 자리가 없음.

## ⚠️ 주의사항

**블로킹 리스크**
- 반경 기반 관광지 조회 API의 정확한 경로/파라미터명이 아직 백엔드와 최종 확인되지 않음 — 잠정 스펙(`GET /api/places/external/nearby`)으로 `PlacesApi` 메서드를 우선 구현하되, 실제 연동/QA 단계에서 400/404가 발생하면 백엔드 확인 후 경로만 교체하면 되도록 메서드 시그니처와 호출부를 분리해 둘 것.

**기술적 위험**
- Kakao Local API 호출 실패와 `resolveRegion`/관광지 조회 API 실패를 같은 "일시적 오류" 화면으로 묶을지, `locationFailed`에 Kakao 실패를 포함할지는 전략 문서에서 이미 결정(전자는 `locationFailed`, 후자 둘은 `placesFailed`)했으나, 구현 시 `KakaoLocalApiService` 예외와 백엔드 API 예외(`ApiError`)의 타입이 다르므로 `_run()`의 try/catch 분기에서 단계별로 정확히 구분해 상태를 설정해야 함.
- `_run()`이 `await`를 여러 번 거치는 긴 체인이므로, 매 `await` 이후 `if (!mounted) return;` 누락 시 dispose된 위젯에 `setState` 호출 오류 발생 가능 — `location_permission_mockup_screen.dart`의 기존 `_refreshStatus`가 이미 이 패턴을 쓰고 있으니 그대로 계승.
- macOS는 `permission_handler` 미지원이라 `LocationPermissionService`가 Geolocator 권한 API로 폴백하는데, `permanentlyDenied` 대응 버튼(`openAppSettings`)이 macOS에서 정상 동작하는지 별도 확인 필요(#30에서 이미 다룬 이슈이므로 회귀만 확인).

**비즈니스 위험**
- "관광지 후보"의 정렬/개수 제한 기준 미정 — 이번 구현은 백엔드가 반환하는 리스트를 그대로 상위로 전달하는 데까지만 책임지고, 정렬/필터링 로직은 넣지 않음(범위 외 임의 구현 방지).
- 서비스 지역 외 사용자의 "충청남도 전용 기능 비활성화" 범위는 이번 화면(안내+메인 복귀)까지만 구현하고, 실제 지도/코스추천/방문인증 화면에서의 비활성화 처리는 각 기능 구현 시점으로 명시적으로 이관.
