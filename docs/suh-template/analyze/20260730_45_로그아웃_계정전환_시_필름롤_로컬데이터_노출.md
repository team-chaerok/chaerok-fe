#### 2️⃣ 핵심 구현 (파일별 변경 요약)

**스키마**
- `lib/core/database/tables/film_rolls_table.dart`: `IntColumn get userId => integer().nullable()();` 추가. Nullable로 두는 이유는 마이그레이션 직후 "아직 귀속되지 않은" 레거시 행을 표현하기 위함(아래 백필 전략 참고). 신규 생성 행은 항상 실제 계정 id를 채운다.
- `lib/core/database/local_database.dart`: `schemaVersion` 1 → 2. `migration.onUpgrade`에 `from < 2` 분기로 `m.addColumn(filmRolls, filmRolls.userId)` 추가(기존 `onCreate`의 `_createActiveFilmRollUniqueIndex()` 호출부는 그대로 유지).

**계정 식별자 로컬 저장**
- `lib/core/config/app_preferences.dart`: 기존 패턴 그대로 `_keyCurrentUserId` 상수 + `getCurrentUserId()`/`setCurrentUserId(int?)` 추가(다른 setter들처럼 `null`이면 `remove`, 아니면 `setInt`).

**계정 동기화 진입점 (신규)**
- 로그인 직후·스플래시 세션 재개 시 공통으로 쓸 작은 동기화 로직이 필요. `UsersApi.getMyInformation()`으로 현재 계정을 조회하고, `AppPreferences`에 저장된 이전 값과 비교해:
  - 이전 값이 `null`(첫 실행 또는 이번 마이그레이션 직후) → 계정 id 저장 + 레거시 미귀속 행 1회 귀속(`claim`) 수행.
  - 이전 값이 있고 다르면(계정 전환) → 계정 id만 갱신(귀속 로직은 스킵 — 이미 귀속된 레거시 행은 최초 로그인 계정 소유로 확정된 상태 유지).
  - 이전 값과 같으면 → no-op.
  - 배치 위치는 `lib/features/auth/`(예: `lib/features/auth/domain/usecase/sync_current_account_use_case.dart`) 신설을 제안 — 로그인 화면과 스플래시 화면 양쪽에서 재사용.
  - **레거시 백필을 여기서 수행하는 이유**: 전략 문서에서는 "마이그레이션 시점의 로그인 계정으로 backfill"이라 결정했으나, 실제 Drift `MigrationStrategy.onUpgrade` 콜백 안에서 네트워크 호출(`/api/users/me`)을 하는 것은 DB 계층과 인증 네트워크 계층을 부적절하게 결합시키고 실패 시 DB 오픈 자체를 막을 위험이 있다. 대신 컬럼은 `nullable`로 추가만 하고(순수 로컬 스키마 변경), 앱이 정상적으로 계정을 확인할 수 있는 첫 시점(로그인 성공 또는 스플래시의 인증된 세션 재개)에 "귀속되지 않은 행이 있으면 지금 로그인된 계정 소유로 확정"하는 방식으로 옮긴다. 최종 결과(레거시 행이 마이그레이션 시점 활성 계정에 배정됨)는 전략 문서의 의도와 동일하고, 실행 위치만 더 안전한 지점으로 옮긴 것이다.

- (선택) `AppPreferences`의 `getCurrentUserId`/`setCurrentUserId(null)` 왕복 테스트 — 기존 다른 getter/setter들처럼 전용 테스트가 없는 상태이므로 필수는 아니나 추가 시 일관성 있음.
- `login_screen`/`splash_screen`/`settings_screen`은 현재 위젯 테스트가 전혀 없어(오케스트레이션 호출 추가 수준) 이번 변경만을 이유로 신규 위젯 테스트를 강제하지는 않되, 이슈 재현 시나리오는 데이터소스/리포지토리 레벨 테스트로 이미 충분히 커버됨.

### ⚠️ 주의사항

- **레거시 백필 정확도 한계**: 이미 이 버그로 두 계정 데이터가 한 기기에 섞여 있던 사용자는, 첫 로그인 계정이 모든 미귀속 행을 가져가므로 그 시점에 실제로는 다른 계정 소유였던 행도 잘못 귀속될 수 있다. 스키마가 원래 계정 정보를 남기지 않아 완전한 사후 복구는 불가능 — 이번 수정 이후 신규 데이터부터 정확한 격리가 보장되는 것이 현실적 목표.
- **동기화 실패 시 일시적 전체 미노출**: 로그인/스플래시 동기화(`/api/users/me`) 호출이 실패하면 `current_user_id`가 갱신되지 않아 "모르면 아무것도 노출 안 함" 기본값에 따라 필름롤 목록이 일시적으로 비어 보일 수 있다. 로그인/앱 사용 자체를 막지는 않고, 다음 성공적인 동기화에서 자연 복구된다. 사용자에게 혼란을 줄 수 있어 UX 관점에서 재시도/안내가 필요한지는 `/implement` 단계에서 별도 판단 필요.
- **저장공간 누적**: 필터링만 하고 삭제하지 않으므로 다른 계정 소유의 과거 사진 파일/행은 기기에 계속 남는다(전략 문서에서 이미 수용한 트레이드오프, 별도 이슈로 정리 제안).
- **`claimLegacyData`의 인터페이스 노출 위치**: 도메인 리포지토리 인터페이스에 넣을지, 데이터소스 전용으로 감출지는 이번 분석에서 결론을 내리지 않았다 — `/implement` 시작 시 확정 필요.
- **동시성**: `findOrCreateActiveByRegion`은 이미 트랜잭션(`_db.transaction`, 45줄)과 부분 유니크 인덱스로 동시 호출을 방어하고 있음 — `userId` 필터 추가가 이 보호를 깨지 않는지(유니크 인덱스가 지역코드+상태 기준이라 계정별로 조건을 더 좁히는 방향이므로 기존 보장을 약화시키지 않음) 확인 완료.
