### 📊 분석 요약

**감지된 프로젝트 타입**: Flutter (`pubspec.yaml`, `lib/` 구조 확인)
**주요 기술 스택**: Dart/Flutter, `dio`(HTTP), `flutter_secure_storage`(토큰 저장), `google_sign_in ^7.2.0`, `kakao_flutter_sdk_user ^1.10.0`. 상태관리 패키지 없음(Provider/Riverpod/Bloc 미사용), 라우팅도 `Navigator.push(MaterialPageRoute(...))` 직접 호출 방식.
**코드 스타일**: `lib/data/remote/*_api.dart`는 `private 생성자(`ClassName._()`) + static 메서드` 패턴(`AuthApi`, `HealthApi`). 화면 위젯은 API 호출·상태 정리·네비게이션을 위젯 내부에서 직접 처리(별도 유스케이스/레포지토리 계층 없음). 에러는 `DioException.error`에 `ErrorInterceptor`가 심어준 `ApiError`를 꺼내 메시지로 사용.

**참고**: 현재 체크아웃된 브랜치가 `20260707_#21_로그아웃_및_회원탈퇴_로직_구현_및_API_연동`으로, 바로 이 작업을 위해 만들어진 브랜치임을 확인함(원격에 동일 이슈의 `#22` 브랜치, 형제 이슈인 `#23_내_정보_조회_닉네임_수정` 브랜치도 존재하나 둘 다 `main` 대비 커밋 없이 비어있음 — 참고할 기존 구현 없음).

### 🔍 현재 상태

**이미 구현되어 있는 것**:
- 로그아웃: `home_screen.dart:17-37`의 `_onLogoutTap`에서 `AuthApi.logout()` 호출(실패해도 무시) → `TokenStorage.instance.clear()` → `LoginScreen`으로 `pushReplacement`. 이 로직 자체는 [/plan](../plan/20260711_20260707_로그아웃_회원탈퇴_기능_구현.md) 문서에서 확인한 대로 정상 동작 중이며 이번 작업에서는 위치만 이전한다.
- `DioClient.delete<T>(path, {fromJson})` — 파라미터 없는 DELETE 요청을 이미 지원(`lib/core/network/dio_client.dart:79-85`). 새 회원탈퇴 API가 그대로 재사용 가능.
- `lib/data/models/user_response.dart`, `update_nickname_request.dart` — `UserResponse`, `UpdateNicknameRequest` 모델이 이미 존재하지만 이를 호출하는 API 클래스가 없음(형제 이슈 `#23`용으로 미리 추가된 모델로 추정). 이번 작업 범위는 아니지만, `UsersApi`를 새로 만들 때 같은 파일에 `GET /api/users/me`, `PATCH /api/users/me` 자리가 후속으로 들어올 것을 감안해 파일을 설계한다(단, 이번 구현 범위는 `withdraw()`만).
- 인증 헤더/401 처리: `AuthInterceptor`가 모든 요청에 accessToken을 자동으로 붙이고 401 시 refresh 후 재시도함 — `UsersApi.withdraw()`도 별도 처리 없이 이 인터셉터를 그대로 탄다.
- 에러 → 메시지 변환 패턴: `login_screen.dart:52-57`의 `_errorMessage(Object e)` — `e is DioException && e.error is ApiError` 체크 후 `ApiError.toString()` 사용. 신규 화면에서도 동일 패턴 재사용.

**없는 것**:

  - `UserApi.instance.unlink()` — `kakao_flutter_sdk_user-1.10.0/lib/src/user_api.dart:253` 존재, `Future<UserIdResponse>` 반환, 내부적으로 토큰도 정리함.

#### 2️⃣ 핵심 구현 (파일별 변경 요약)

**[신규] `lib/data/remote/users_api.dart`**
```dart
class UsersApi {
  const UsersApi._();

  /// [회원탈퇴] API 호출
  /// 인증된 사용자의 계정과 인증 관련 데이터를 삭제합니다.
  static Future<void> withdraw() async {
    await DioClient.instance.delete<void>('/api/users/me');
  }
}
```

### ⚠️ 주의사항

- **SDK 연동 해제 실패를 탈퇴 실패로 오인하지 말 것**: `UsersApi.withdraw()`가 성공한 시점에 서버 계정은 이미 삭제됨. 이후 `disconnect()`/`unlink()`가 실패해도 사용자에게는 탈퇴가 정상 완료된 것으로 안내해야 함(전략 문서 "기술적 위험" 항목과 동일).
- **탈퇴 실패 시 부분 정리 금지**: `UsersApi.withdraw()` 호출 자체가 실패(네트워크 오류, 서버 오류 등)하면 `TokenStorage.clear()`를 호출하면 안 됨 — 로그아웃(`_onLogoutTap`)과 달리 탈퇴는 실패 시 로컬 상태를 그대로 유지해야 서버-클라이언트 상태가 어긋나지 않음.
- **`home_screen.dart` 변경 시 회귀 주의**: `_onLogoutTap` 제거 후 관련 `import`가 안 쓰이는 채로 남으면 린트 경고 발생 — 반드시 함께 정리.
- **에러 메시지 획득 경로**: `ErrorInterceptor`가 이미 `DioException.error`를 `ApiError`로 치환해주므로, `UsersApi.withdraw()`를 감싸는 `try/catch (DioException e)`에서 `e.error is ApiError`만 확인하면 됨 — 별도 파싱 로직 불필요(`login_screen.dart:52-57` 참고).
- **`GoogleSignIn.instance`/`UserApi.instance` 싱글톤 접근 시점**: `AppStartup.initialize()`가 앱 시작 시 이미 초기화하므로 별도 초기화 호출 불필요하지만, 위젯 테스트 시 mock 없이 실제 SDK를 호출하면 플랫폼 채널 오류가 날 수 있음 — 테스트 작성 시 `GoogleAuthService`/`KakaoAuthService`를 인터페이스로 감싸 mock 가능하게 할지 여부는 구현 단계에서 검토(과설계 방지를 위해 필요할 때만 도입).
- **`UserResponse`/`UpdateNicknameRequest` 모델은 이번 범위 밖**: `users_api.dart`를 만들 때 회원 정보 조회/닉네임 수정 메서드까지 욕심내지 말 것 — 형제 이슈(`#23`)의 범위이며, 이번엔 `withdraw()`만 추가한다.
