## 📊 분석 요약

**감지된 프로젝트 타입**: Flutter (`pubspec.yaml`, `lib/`)
**주요 기술 스택**: Dart null-safety, Dio 기반 REST 클라이언트(`DioClient`), Drift(로컬 SQLite, `AppDatabase`), SharedPreferences(북마크), 별도 상태관리 라이브러리 없음(StatefulWidget + setState 기반 Controller 패턴)
**코드 스타일**:

- API 클라이언트: `class XxxApi { const XxxApi._(); static Future<...> method(...) }` — 정적 메서드 전용, private 생성자
- 유스케이스: `class XxxUseCase { const XxxUseCase(deps); Future<...> call(...) }` — callable 클래스
- Repository: 도메인 interface(`FilmRollRepository`) + 구현체(`FilmRollRepositoryImpl`) 분리, `FilmRollModule`이 수동 DI 조립
- **다중 결과 타입 표현**: `sealed class`가 아니라 **`enum` + 단일 결과 클래스(private named 생성자 + nullable 필드)** 패턴을 씀 — 예: `ExitFilmRollResult`(`ExitOutcome` enum + `.developing()`/`.expired()` named 생성자). 이번 작업에서 신규 도입할 "코스 선택 결과" 타입도 이 패턴을 따라야 함(sealed class는 이 코드베이스에 선례가 없음).
- 화면 State: `Navigator.push<T>` 결과를 그대로 pop 값으로 받아 컨트롤러에 위임, 에러는 `log(..., name: _tag)` + `ScaffoldMessenger` 스낵바
- 문서화: 클래스/메서드 상단에 "왜"를 설명하는 한국어 doc-comment, 자명한 것은 주석 없음

## 🔍 현재 상태

### 코스 선택 흐름 (추천 전용)

- `CourseSelectionScreen(regionId)` → `CoursesApi.getRecommendedCourses(regionId)` → 카드 탭 시 `Navigator.pop(CourseResponse)`.
- `CourseResponse.courseId`는 서버가 안 주는 값이라 장소 구성을 JSON 인코딩해 **합성한 문자열**(코스 변경 차단 판단용, `course_response.dart:26-38`).
- `SelectCourseUseCase.call(filmRollId, course)` → `CourseCandidatePlace.fromCoursePlaceResponse`(좌표 필수 검증) → `FilmRollRepository.selectCourse(filmRollId, courseId, courseTitle, places)`.
- `FilmRollRepositoryImpl.selectCourse`: 방문/사진 기록이 있고 `row.selectedCourseId != courseId`면 `CourseChangeBlockedException`, 아니면 트랜잭션으로 기존 장소 삭제 후 재삽입.

### CourseSelectionScreen 호출부 3곳 (모두 `Navigator.push<CourseResponse>` 패턴, 서로 다른 소비 방식)

| 파일                                                                                                            | 소비 방식                                                                                                                       |
| --------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| `lib/features/film_roll/presentation/page/film_roll_screen.dart:93-107` (`_onSelectCourseTap`)                  | `_controller.selectCourse(selected)` (컨트롤러 경유)                                                                            |
| `lib/features/explore/presentation/widgets/film_roll_progress_view.dart:151-161` (`_onSelectCourseTap`)         | `_controller.selectCourse(selected)` (컨트롤러 경유, 동일 패턴)                                                                 |
| `lib/features/film_roll/presentation/widgets/film_roll_entry_flow.dart:49-69` (`pushCourseSelectionAndConfirm`) | `FilmRollModule.instance.selectCourse(...)` **유스케이스 직접 호출** — 위치 인증 직후 자동 연결 플로우(이슈 #75)가 이 함수를 씀 |

### 백엔드 연동 미사용 API (`lib/data/remote/courses_api.dart`)

- `createCourse(CourseCreateRequest)` → `SelectedCourseResponse` (장소 1~3개, 기존 ACTIVE는 서버가 INACTIVE 처리 후 재생성)
- `addActiveCoursePlaces` — 이번 이슈 범위 밖(코스 "추가 편집", 별도 이슈감)
- `getActiveCourse` — 이번 이슈에서 "이미 ACTIVE 코스 있음" 판단에 필요할 수 있음

### ⚠️ 핵심 데이터 갭: 좌표 정보 부재

- `CourseCreateRequest.places`는 `CoursePlaceSaveRequest`(`placeId?`, `externalPlaceId?`, `source?`, `title`, `categoryGroup`, `categoryDetail?`, `address?`, `latitude?`, `longitude?`, `placeUrl?`) 형태로 **보낼 때는** 좌표를 포함할 수 있지만,
- 서버 응답 `SelectedCourseResponse.places`는 `SelectedCoursePlaceResponse`(`placeId`, `source`, `title`, `categoryGroup`, `categoryDetail?`, `address`, `sequence`)로 **위도/경도가 없음**.
- 반면 `SelectCourseUseCase`가 로컬 DB에 저장하는 `CourseCandidatePlace`는 위도/경도가 **필수**(`CourseCandidatePlace.fromCoursePlaceResponse`에서 없으면 `InvalidCoursePlaceException`).
- ⇒ **`createCourse` 응답만으로는 로컬 DB 저장(`FilmRollPlaces`)에 필요한 좌표를 채울 수 없다.** 사용자가 피커에서 고른 원본 장소 데이터(좌표 포함)를 별도로 들고 있다가, 서버 응답은 `courseId`/`title`/`sequence`(정렬 검증용)만 취해 조합해야 한다.

### 장소 소스 3종 현황

- 관광지 목록: `PlacesApi.getPlaces(regionId)` → `List<PlaceListResponse>`
- 검색: `PlacesApi.searchPlaces(regionId, keyword)` → `List<PlaceSearchResponse>`
- 정규화 모델: `ExplorePlace`(`lib/features/explore/domain/explore_place.dart`)가 위 두 응답을 통합 — `categoryGroup`/`categoryDetail`(enum), `source`, `serverId`, `identityKey`(외부ID 우선) 보유. 단, `externalPlaceId`(tourContentId/kakaoPlaceId)를 **별도 필드로 노출하지 않고** `identityKey` 문자열 안에만 인코딩함.
- 북마크: `BookmarkStore`/`BookmarkedPlace`(`lib/features/explore/data/bookmark_store.dart`)는 **로컬 전용**, SharedPreferences JSON 배열. 저장 필드: `identityKey`, `title`, `categoryLabel`, `latitude`, `longitude`, `imageUrl`뿐 — `categoryGroup`(wire 값), `source`, `placeId`/`externalPlaceId`가 없어 `CoursePlaceSaveRequest`를 채울 수 없음.
- 북마크 진입점: **전용 북마크 목록 화면/오버레이가 현재 없음.** `ExploreScreen`의 탐색 모드 카드마다 북마크 토글 아이콘(`_BookmarkButton`, `explore_screen.dart:583-585, 614-`)만 존재하고, `_bookmarkedKeys`로 토글 상태만 표시함.

## 🎯 구현 목표

1. `CourseSelectionScreen`에 추천/직접 만들기 탭을 추가하고, 직접 만들기 모드에서 관광지 목록·검색·북마크 3종 장소를 통합 피커로 1~3개 선택·순서 지정할 수 있게 한다.
2. 선택 확정 시 `CoursesApi.createCourse`로 ACTIVE 코스를 생성하고, **원본 좌표 데이터를 보존한 채** 기존 필름롤 코스 확정 로직(로컬 DB 저장, 방문 기록 있을 시 변경 차단)과 동일한 보장으로 연결한다.
3. 기존 추천 코스 플로우와 3개 호출부(`film_roll_screen`, `film_roll_progress_view`, `film_roll_entry_flow`)를 회귀 없이 유지한다.
4. 북마크를 코스 생성에 실제로 활용 가능하게 만든다(현재는 죽은 기능).

### 3️⃣ 테스트 작성 (시나리오)

- `SelectCustomCourseUseCase`: 정상 흐름(1~3개 장소) / 좌표 없는 장소 포함 시 예외 전파 / `createCourse` 실패(네트워크·422) 시 로컬 DB 미변경 확인 / 이미 방문 기록 있는 필름롤에서 다른 커스텀 코스로 바꾸려 할 때 `CourseChangeBlockedException` / 서버 응답 `sequence`가 요청 순서와 다를 때 방어적 재정렬 동작.

## ⚠️ 주의사항 (구현 전 확정 필요한 미해결 질문)

1. **코스 제목 생성 규칙**: `CourseCreateRequest.title`을 사용자가 직접 입력하게 할지, 자동 생성(예: 대표 장소명 + "코스")할지 UX 결정 필요. 백엔드 필수값이라 빈 문자열로 보낼 수 없음.
2. **ACTIVE 코스 대체 확인 다이얼로그의 판단 시점**: "기존 ACTIVE 코스가 있으면 대체 확인"을 위해 확정 버튼을 누르기 전에 매번 `getActiveCourse`를 선조회할지(추가 API 호출, 최신 상태 보장), 로컬 필름롤의 `selectedCourseId` 존재 여부로 판단할지(호출 없음, 다른 기기에서 만든 ACTIVE 코스는 놓칠 수 있음). 서버가 어차피 INACTIVE 처리 후 재생성하므로 실패하지는 않지만, "안내 없이 조용히 대체"는 이슈 요구사항 위반.
3. **북마크 진입점 UI 형태**: 현재 전용 북마크 목록/오버레이 화면이 없음(카드별 토글 아이콘만 존재). (a) `ExploreScreen`에 "북마크만 보기" 필터/바텀시트를 신설할지, (b) 각 북마크 카드에 보조 액션(길게 누르기 메뉴 등)만 추가해 커스텀 코스 피커의 "북마크" 탭으로 보내는 것으로 충분할지 결정 필요 — UI 작업량 차이가 큼.
4. **`sequence` 신뢰 여부**: `SelectedCourseResponse.places[i].sequence`가 요청 순서와 항상 1:1 대응하는지 백엔드 문서/실측 확인 필요. 확인 전까지는 `sequence`로 재정렬하는 방어 코드를 반드시 넣는다(요청 순서를 맹신하면 장소-좌표 매칭이 틀어질 위험).
5. **`ExplorePlace.externalPlaceId` 신규 필드**와 기존 `identityKey` 합성 로직이 값 불일치를 일으키지 않도록, `identityKey` 계산은 계속 `source`/`serverId`/`tourContentId`/`kakaoPlaceId` 원본 파라미터를 쓰고 `externalPlaceId`는 별도 필드로만 노출(파싱 역산 금지).
