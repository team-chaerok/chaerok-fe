### 2) 전략 문서(P0) 대비 실제 API 계약과의 세부 불일치 — 구현 착수 전 확정 필요

**① `RegionCode`/`RegionNormalizer`의 입력 소스**
전략 §4 P0는 "문자열→RegionCode, contains 금지·행정구역 필드 우선"이라고 명시했는데, 실제 코드에는 두 종류의 "행정구역 문자열"이 존재한다:
- `KakaoLocalApiService.resolveAdministrativeRegion()`이 반환하는 **기기 좌표 기반, 미검증** 문자열 (`administrativeRegion.provinceName/cityCountyName`)
- `RegionsApi.resolveRegion()`이 반환하는 **서버 검증 완료** 문자열 (`RegionResponse.cityCountyName`, `serviceArea==true`일 때만 신뢰 가능) + `regionId`(opaque int)

선행 분석 문서(§3)는 "서버가 이미 `regionId`/`serviceArea`로 처리하므로 클라이언트 enum이 불필요하다"고 결론 냈었지만, 이번 전략 문서는 로컬 DB 파티션 키·필름롤 제목 표시용으로 `RegionCode`가 필요하다는 새 요구(로컬이 원본이므로 로컬에도 지역 키가 있어야 함)로 갱신되었다. 두 문서가 완전히 배치되지는 않는다 — **`RegionNormalizer`의 입력을 `RegionResponse.cityCountyName`(서버 검증 후 값)으로 한정**하면 두 요구를 동시에 만족한다.
→ **권장**: `RegionNormalizer.fromCityCountyName(RegionResponse.cityCountyName)`만 노출하고, Kakao 원시 문자열을 직접 정규화하는 경로는 만들지 않는다. `FilmRolls.regionCode`는 표시/그룹핑용 로컬 키로 두되, 서비스 지역 여부 판정 자체는 계속 `RegionResponse.serviceArea`(서버)가 담당한다.

**② 선택된 코스 장소의 이미지 URL 소스 부재**
전략 §7 스키마의 `FilmRollPlaces.imageUrl`은 `CoursePlaceResponse`(추천 코스 후보, `getRecommendedCourses` 응답)로부터 채우는 것으로 보이지만, 실제 `CoursePlaceResponse`에는 이미지 필드가 없다(`placeUrl`만 존재 — Kakao/상세 링크 URL로 추정, 이미지 아님). 이미지 URL은 `PlaceListResponse.firstImageUrl`에만 존재하며, 이는 `PlacesApi.getPlaces`/`getExternalPlaces` 응답에서만 온다.
→ **권장**: `SelectCourseUseCase`에서 코스 확정 시, 선택된 `CoursePlaceResponse.placeId`(non-null인 경우만)를 이미 조회해 둔 `PlaceListResponse` 목록(지역 진입 시 `getExternalPlaces` 결과, 홈/필름롤 화면에서 캐시 보관)과 매칭해 `imageUrl`을 보강한다. `placeId`가 null(Kakao 소스, DB 미등록 장소)이면 이미지 없이 플레이스홀더로 표시—TODO로 명시.

**③ `latitude`/`longitude` nullable**
`CoursePlaceResponse.latitude/longitude`는 `double?`(nullable)이다. 전략 §7 스키마는 `latitude/longitude`를 필수 컬럼처럼 적어놓았는데, 실제로는 null 가능성을 스키마/매핑 코드 양쪽에서 처리해야 한다(컬럼을 nullable로 정의하거나 매핑 시 기본값 처리 정책 확정 필요).

**④ 카메라 권한 미선언 (실제 확인됨)**
`ios/Runner/Info.plist`에는 `NSLocationWhenInUseUsageDescription`만 있고 카메라 관련 `NSCameraUsageDescription`이 없음. `android/app/src/main/AndroidManifest.xml`에도 `ACCESS_FINE_LOCATION`/`ACCESS_COARSE_LOCATION`만 있고 `android.permission.CAMERA`가 없음 — 전략 §10에서 위험요소로 지목한 내용이 실제로 확인됨. 1단계(의존성 추가) 직후 권한 선언 추가가 선행되어야 `camera` 패키지 초기화가 실기기에서 크래시 없이 동작한다.

### 3) 아키텍처 계층 신설 관련

이 프로젝트에는 Repository/UseCase 계층이 전혀 없다(모든 화면이 `XxxApi` 정적 메서드를 직접 호출). 이번 기능이 최초로 이 계층을 도입하므로, 기존 "정적 메서드 스타일"을 그대로 따를 수 없는 지점(DB 인스턴스/DAO는 상태를 가지므로 정적일 수 없음)에서는 `DioClient.instance` 싱글톤 패턴을 그대로 차용해 `AppDatabase.instance`, `FilmRollRepository`(생성자에서 DAO 주입받는 일반 클래스, 화면에서 `FilmRollRepository(AppDatabase.instance)`처럼 직접 생성 — Provider/GetIt 등 DI 프레임워크 미도입) 형태로 구성하는 것이 기존 스타일과 가장 자연스럽게 맞는다.
