## 코드 리뷰: 로그아웃/계정전환 시 필름롤 로컬 데이터 노출 수정

**범위**: 파일 단위(이번 세션에서 구현한 변경분 전체) — 스키마 마이그레이션, 계정 스코프 필터링, 로그인/스플래시 동기화, 로그아웃 정리, 신규/수정 테스트 12개 파일.

### 🚨 Critical (즉시 수정)
없음.

### ⚠️ Major (배포 전 수정)

**`lib/features/film_roll/data/local/film_roll_local_data_source.dart:77-79`(`deleteById`), `lib/features/film_roll/data/repository/film_roll_repository_impl.dart:194-197`(`deleteFilmRoll`)** — 삭제 경로에 계정 소유 검증이 없다.
- 문제: 이번 변경으로 `findAll`/`findById`/`findActiveByRegion`/`watchById`는 모두 현재 로그인 계정으로 스코핑됐지만, `deleteById`는 여전히 `WHERE id = ?`만으로 삭제한다. `deleteFilmRoll(filmRollId)`도 소유권 확인 없이 곧바로 `_photoStorage.deleteFilmRollDirectory(filmRollId)` + `_filmRollDs.deleteById(filmRollId)`를 호출한다.
- 영향: 지금은 `DeleteFilmRollUseCase`를 호출하는 화면이 없어(grep 결과 UI 호출부 없음) 당장 악용 경로는 없지만, 이 use case는 이미 `FilmRollModule`에 조립되어 있어 다음에 삭제 버튼이 붙는 순간 "다른 계정 소유의 id를 어떤 경로로든 알게 되면(예: 계정 전환 전 캐시된 위젯 상태) 그 계정의 필름롤을 삭제할 수 있는" 구멍이 그대로 열린다. 계정 격리라는 이번 수정의 목적을 조회에는 적용하고 변경(삭제)에는 적용하지 않아 일관성이 깨진다.
- 해결: `deleteById`에 `currentUserId()`를 읽어 `t.userId.equals(userId)` 조건을 추가하거나, 최소한 `deleteFilmRoll`에서 삭제 전 `findById(filmRollId)`(이미 계정 스코핑됨)로 존재를 확인한 뒤에만 삭제하도록 가드를 추가 권장. `update()`(selectCourse/completeFilmRoll 경유)는 호출 전에 이미 스코핑된 `findById`를 거치므로 상대적으로 안전하지만, 동일한 이유로 `deleteById`만 예외로 남기지 않는 편이 이번 변경의 의도와 맞다.

**`lib/features/film_roll/data/local/film_roll_local_data_source.dart:56-64`(`watchById`)** — 스트림 구독 시점에만 계정을 확인하고, 이후 발행되는 값에는 재확인이 없다.
- 문제: `Stream.fromFuture(currentUserId()).asyncExpand(...)` 구조상 `currentUserId()`는 스트림이 처음 구독될 때 딱 한 번만 평가된다. 클래스 상단 문서(6-13번째 줄)는 "캐싱하지 않고 호출 시점마다 다시 읽는다"고 명시하는데, `watchById`만 이 원칙에서 벗어나 사실상 "구독 시점에 캐싱"된다.
- 영향: 현재 `watchById`를 소비하는 UI가 없어(grep 결과 `StreamBuilder` 등 실사용처 없음) 당장 재현되진 않지만, 향후 상세 화면에서 이 스트림을 구독한 채로 로그아웃→다른 계정 로그인이 같은 프로세스 안에서 일어나면(위젯이 dispose되지 않는 구조라면) 이전 계정 컨텍스트로 계속 구독하게 될 수 있다.
- 해결: 계정 변경을 별도로 감지해 스트림을 재구성하거나(예: `currentUserId()`를 주기적/이벤트 기반으로 다시 읽어 `switchMap` 유사 처리), 최소한 문서 주석에서 `watchById`는 이 보장의 예외라는 점을 명시.

**테스트 커버리지 공백** — 이번 변경에서 가장 미묘한 두 지점이 테스트되지 않았다.
- `watchById`의 계정 스코핑(및 위 재구독 이슈)에 대한 테스트가 `film_roll_local_data_source_test.dart`에 없음(findAll/findById/findActiveByRegion/claimUnassigned만 커버).
- `lib/features/auth/data/current_account_sync.dart`의 핵심 분기(이전 계정 id가 null일 때만 `claimLegacyData` 호출, 있으면 스킵, `UsersApi` 실패 시 예외를 삼키고 계속 진행) — "1회만 귀속"이라는 이번 수정의 핵심 불변식을 담당하는 클래스인데 전용 테스트가 하나도 없다.

### 💡 Minor (개선 권장)

- **`film_roll_repository_impl.dart:52,63`** — `findOrCreateActiveByRegion` 안에서 `currentUserId()`를 두 번 읽는다(`_filmRollDs.findActiveByRegion` 내부에서 한 번, insert용으로 직접 한 번 더). 극히 낮은 확률이지만 두 호출 사이에 계정이 바뀌면 "다른 계정 기준으로 조회했는데 또 다른 계정으로 생성"되는 불일치가 이론적으로 가능하다. 트랜잭션 시작 시 한 번만 읽어 재사용하는 편이 의도를 더 명확히 드러낸다.
- **`lib/features/auth/data/current_account_sync.dart`** — auth 기능이 `FilmRollModule`(film_roll 기능)을 직접 참조한다. 이 프로젝트의 다른 auth 코드(`login_screen.dart`, `settings_screen.dart` 등)는 지금까지 `TokenStorage`/`*Api`/`AppPreferences`처럼 core 계층만 참조해왔는데, 이번 클래스만 기능 간 경계를 가로지른다. 의도적 선택이었다면 문제 없으나, 다음에 이 파일을 보는 사람이 위치 선정을 다시 고민하지 않도록 클래스 주석에 "왜 여기서 FilmRollModule을 직접 참조하는지" 한 줄을 추가하면 좋겠다.
- **네이밍 불일치**: 도메인 인터페이스는 `claimLegacyData`(`film_roll_repository.dart`)인데 실제 구현은 `claimUnassigned`(`film_roll_local_data_source.dart`)에 위임한다. 같은 동작에 두 개의 다른 동사를 쓰고 있어 처음 읽는 사람에게는 둘이 다른 걸 하는지 잠깐 헷갈릴 수 있다.
- **`splash_screen.dart:89-92`** — 이미 인증된 세션으로 앱을 재개할 때마다 `CurrentAccountSync.sync()`가 매번 `/api/users/me`를 호출한다. 로그인 시점에 이미 `currentUserId`가 정상 저장돼 있다면(정상 흐름에서는 항상 그렇다) 이 네트워크 호출은 매 앱 실행마다 불필요한 지연을 더한다. `AppPreferences.instance.getCurrentUserId()`가 이미 non-null이면 네트워크 호출 없이 스킵하고, null일 때만(마이그레이션 직후 등) 호출하도록 최적화할 여지가 있다.

### ✅ Positive (잘한 점)

- `findAll`/`findById`/`findActiveByRegion`에 "현재 계정을 모르면 전체 대신 빈 결과"라는 안전 기본값을 일관되게 적용해, 이번 버그류가 새 코드에서 같은 방식으로 재발하기 어렵게 만들었다.
- 스키마 마이그레이션에서 `userId`를 nullable로 두고, 실제 계정 귀속(`claim`)은 Drift `onUpgrade` 콜백이 아니라 앱 계층(로그인/스플래시)에서 수행하도록 분리해 DB 마이그레이션과 네트워크 호출을 결합시키지 않은 점이 좋은 판단이다.
- 새 코드가 프로젝트 기존 관례(선택적 DI 파라미터 + `?? X.instance`, static 유틸리티 클래스 스타일)를 그대로 따라 스타일 일관성이 높다.
- `film_roll_local_data_source_test.dart`가 이슈의 실제 재현 시나리오(두 계정, 교차 조회 차단)를 그대로 테스트로 인코딩했고, 스키마 변경으로 깨질 기존 테스트 2곳을 정확히 찾아 함께 수정했다.
- `flutter analyze` 무경고, `dart format` 적용, `flutter test` 전체 통과 확인됨.
