### 💡 Minor (개선 권장)

**`lib/data/models/place_list_response.dart` / `place_search_response.dart` / `place_detail_response.dart`** — `fromJson`에 필드 파싱 로직 중복
현재 세 클래스 모두 `id`, `title`, `address`, `latitude`, `longitude`, `firstImageUrl`, `categoryGroup`, `categoryDetail`, `source`, `tourContentId`, `kakaoPlaceId`를 거의 동일한 코드로 반복 파싱합니다. 다만 이는 계획 단계에서 의도적으로 검토한 트레이드오프입니다 — `PlaceListResponse`엔 있고 `PlaceSearchResponse`엔 없는 `isRepresentative`, `PlaceDetailResponse`에만 있는 `regionId`/`overview`/`lDong*`/`lclsSystm*` 때문에 공통 베이스 클래스를 두면 오히려 nullable 필드가 늘어나 설계가 복잡해진다고 판단해 상속 없는 독립 클래스를 선택했습니다(`region_response.dart` 등 기존 모델 스타일과도 일치). 지금 시점에는 문제 삼을 수준은 아니지만, 이후 장소 관련 모델이 하나 더 늘어난다면(예: 지도 마커 응답) 공통 필드를 파싱하는 헬퍼 함수 정도는 고려해볼 만합니다.

**`lib/data/remote/places_api.dart`** — 4개 메서드에 대한 단위 테스트 없음
`DioClient`를 목킹해 `getPlaces`/`getPlaceDetail`/`searchPlaces`/`getExternalPlaces`가 배열·객체 응답을 올바르게 모델로 매핑하는지 확인하는 테스트가 없습니다. 특히 배열 응답 처리(`fromJson: (data) => (data as List).map(...)`)는 이번에 이 코드베이스에 처음 도입된 패턴이라, 향후 `DioClient._toApiResponse`의 분기 로직이 바뀌면 조용히 깨질 수 있습니다. 다만 `AuthApi`/`UsersApi`도 테스트가 없는 프로젝트 전반의 기존 상태라 이번 변경만의 문제로 보기는 어렵습니다. `/test` 단계에서 최소한 "배열 응답이 리스트로 매핑되는지", "빈 배열/`null` 응답이 `const []`로 폴백되는지" 두 시나리오는 커버하는 것을 권장합니다.

### ✅ Positive (잘한 점)

- Swagger 스펙을 임의로 재해석하지 않고 필드명·nullable 여부를 그대로 반영함(`lDongRegnCd` 등 백엔드 명명 규칙까지 그대로 유지) — 이후 실제 응답과 대조하기 쉬움.
- `/api/places/external`의 응답 스키마가 `PlaceListResponse`와 완전히 동일하다는 걸 확인하고 불필요한 4번째 모델을 만들지 않은 점 — 요청받지 않은 추상화를 만들지 않는다는 프로젝트 원칙과 일치.
- 배열 응답(`response.data ?? const []`)과 단일 객체 응답(`response.data ?? PlaceDetailResponse.empty()`)의 폴백 방식을 `DioClient._toApiResponse`의 실제 분기 로직(Map vs List)에 맞춰 정확히 구분해서 처리함.
- `AuthApi`/`UsersApi`의 정적 클래스 + private 생성자 + 한국어 doc comment 스타일을 그대로 따라 코드베이스 일관성을 유지함.
