## 🎯 로그아웃/회원탈퇴 기능 구현 전략 문서

### 1. 요약

로그아웃은 이미 `home_screen.dart`에 인라인으로 구현되어 있으나(`AuthApi.logout()` 호출 → `TokenStorage.clear()` → 로그인 화면 이동), 별도 진입 화면이 없어 홈 화면에 로그아웃 버튼만 덩그러니 떠 있는 상태다. 회원탈퇴는 API 연동 코드와 UI가 전혀 없다. 이번 작업은 `설정` 화면을 신설해 로그아웃 버튼을 그리로 옮기고, 신규 백엔드 API(`DELETE /api/users/me`)를 연동한 회원탈퇴 기능을 MVP 수준(확인 다이얼로그 → 즉시 탈퇴 → 로그인 화면 이동)으로 추가한다. 탈퇴 시에는 카카오/구글 SDK 연동 해제(`unlink`/`disconnect`)까지 함께 처리해 재가입 시 계정 선택 창이 다시 뜨도록 한다.

### 2. 배경 및 목적

**문제/필요성**:
- (정정) 로그아웃 자체는 `home_screen.dart:17-37`에 이미 구현되어 있음 — 요청에서 "로그아웃 방법이 없다"고 했으나 실제로는 동작함. 다만 `설정`/`마이페이지` 같은 별도 화면이 없어 홈 화면에 임시로 얹혀 있는 구조.
- 회원탈퇴는 `AuthApi`에 메서드 자체가 없고(`lib/data/remote/auth_api.dart`), 호출할 UI도 없음.
- `google_auth_service.dart`/`kakao_auth_service.dart`에는 로그인(`signIn`)만 있고 연동 해제(`disconnect`/`unlink`) 메서드가 없음 — 탈퇴 후에도 기기에 카카오/구글 세션이 남아 재가입 시 계정 선택 없이 자동으로 이전 계정이 잡힐 수 있음.
- 홈 화면(`lib/features/home/presentation/home_screen.dart`)이 인증/설정 진입점을 겸하고 있어, 새 기능(탈퇴)을 추가하기에 구조적으로 적합하지 않음.

**목표**:
- `설정` 화면을 신설하고, 기존 로그아웃 버튼을 홈 화면에서 이곳으로 이전한다.
- `DELETE /api/users/me` API를 연동해 회원탈퇴 기능을 구현한다.
- 탈퇴 성공 시 로컬 토큰 삭제, 카카오/구글 SDK 연동 해제, 로그인 화면 이동까지 한 흐름으로 처리한다.

**범위**:
- 포함: `AuthApi.withdraw()` 추가, 설정 화면 신설(로그아웃/탈퇴 버튼), 탈퇴 확인 다이얼로그, 탈퇴 성공/실패 처리, 카카오·구글 SDK 연동 해제 메서드 추가.
- 제외(별도 작업): 탈퇴 사유 선택 UI, 재인증(비밀번호/생체인증) 절차, 탈퇴 유예기간(soft delete) 처리 — 모두 백엔드가 즉시 하드 삭제하는 MVP 정책을 따름. 설정 화면 내 다른 메뉴(프로필 수정 등)도 이번 범위 밖.

### 3. 요구사항

**필수 (P0)**:
- `AuthApi`에 `withdraw()` 메서드 추가 — `DELETE /api/users/me`, 파라미터 없음, `AuthInterceptor`가 자동으로 붙이는 accessToken으로 인증.
- 설정 화면 신설 후 홈 화면의 기존 로그아웃 버튼 로직(`_onLogoutTap`)을 그대로 이전 — 동작 변경 없이 위치만 이동.
- 회원탈퇴 버튼 탭 시 확인 다이얼로그 표시 → 확인 시 `AuthApi.withdraw()` 호출 → 성공 시 카카오/구글 SDK 연동 해제 + `TokenStorage.clear()` → 로그인 화면으로 `pushReplacement`.
- 탈퇴 API 실패(네트워크 오류 등) 시 로컬 토큰을 지우지 않고 에러 스낵바 등으로 사용자에게 알림 — 로그아웃과 달리 탈퇴는 "부분 실패"를 허용하면 안 됨(서버에 계정이 남아있는데 로컬만 지워지면 재로그인 시 혼란).

**중요 (P1)**:
- `GoogleAuthService`에 `disconnect()`, `KakaoAuthService`에 `unlink()` 메서드 추가 — 각각 SDK의 `GoogleSignIn.instance.disconnect()` / `UserApi.instance.unlink()`를 감싸며, 실패해도 탈퇴 흐름 자체는 막지 않고 로그만 남김(이미 탈퇴 API가 성공했으므로 서버 계정은 삭제된 상태 — SDK 연동 해제 실패로 탈퇴를 되돌릴 수 없음).
- 로그아웃은 기존과 동일하게 SDK 연동 해제를 하지 않음(백엔드 토큰 폐기만) — 사용자가 명시적으로 범위를 구분함.

**선택 (P2)**:
- 설정 화면에 탈퇴 버튼을 로그아웃과 시각적으로 구분(예: 빨간색 텍스트)해 실수 탭 방지.

### 4. 선택한 접근 방식

**방식**: 새 `lib/features/settings` 피처 디렉토리를 만들어 `SettingsScreen`(StatelessWidget)을 추가한다. 홈 화면에는 설정 화면으로 이동하는 아이콘 버튼만 남기고, 로그아웃 관련 로직(`_onLogoutTap`)은 `SettingsScreen`으로 그대로 옮긴다. 탈퇴 로직(`_onWithdrawTap`)은 동일 화면에 나란히 구현하되, `AuthApi.logout()`과 마찬가지로 화면(위젯) 레벨에서 직접 API 호출 → 상태 정리 → 네비게이션까지 처리한다(현재 프로젝트에 별도 상태관리/유스케이스 계층이 없고, 로그인/로그아웃 로직도 모두 화면에서 직접 처리하는 기존 패턴을 따름).

**이유**:
- 프로젝트에 Provider/Riverpod/Bloc 등 상태관리 패키지가 없고, `login_screen.dart`/`home_screen.dart` 모두 화면 위젯이 API 호출과 네비게이션을 직접 수행하는 일관된 패턴을 쓰고 있음 — 탈퇴만 별도 유스케이스/서비스 계층을 새로 만들면 오히려 기존 코드와 이질적이 됨.
- 로그아웃 로직을 신규 작성하지 않고 "이전"만 하는 이유는, 이미 검증된 동작(토큰 폐기 실패해도 로컬 정리는 진행하는 정책 등)을 그대로 재사용하기 위함 — 굳이 재구현할 이유가 없음.
- 탈퇴는 로그아웃과 달리 "부분 실패 허용 안 함" 정책이 필요해 별도 함수로 분리하되, 같은 화면 안에 두어 사용자가 두 액션의 차이(위험도)를 한눈에 비교할 수 있게 함.

**대안 (왜 선택하지 않았는지)**:
- **홈 화면에 탈퇴 버튼만 추가(설정 화면 미신설)**: 사용자가 명시적으로 설정 화면 신설을 선택함. 또한 홈 화면이 계속 "성공 아이콘 + 로그인 성공 텍스트"라는 임시 placeholder UI를 겸하고 있어, 인증 관련 액션이 계속 쌓이면 화면 책임이 불명확해짐.
- **AuthService/AuthRepository 같은 공용 도메인 계층 신설**: 로그인/로그아웃/탈퇴를 한 클래스로 묶으면 재사용성은 좋아지지만, 현재 로그인 로직도 아직 `login_screen.dart`에 인라인으로 남아있는 상태라 이번 작업 범위에서만 계층을 새로 만들면 절반만 리팩토링된 어중간한 구조가 됨. 상태관리 도입과 함께 전체 인증 로직을 리팩토링할 후속 작업으로 미룸.
- **탈퇴 실패 시에도 로컬 토큰 삭제(로그아웃과 동일 정책)**: 탈퇴 API가 실패했는데 로컬 토큰을 지우면, 서버에는 계정이 살아있지만 앱은 로그아웃 화면으로 튕겨 사용자가 "탈퇴됐다"고 오인할 수 있음 — 데이터 정합성 문제로 채택하지 않음.

### 5. 주요 결정사항

| 결정 | 선택 | 이유 |
|------|------|------|
| 탈퇴 API 스펙 | `DELETE /api/users/me`, 요청 파라미터 없음 | 사용자가 제공한 백엔드 스펙 그대로 반영 |
| `AuthApi.withdraw()` 구현 | `DioClient.instance.delete<void>('/api/users/me')` | 기존 `DioClient.delete<T>`가 이미 파라미터 없는 DELETE를 지원 — 새 클라이언트 메서드 불필요 |
| UI 진입점 | `lib/features/settings/presentation/settings_screen.dart` 신설 | 사용자가 설정 화면 신설(권장안)을 선택 — 홈 화면 로그아웃 버튼도 이 화면으로 이전 |
| 로그아웃 시 SDK 연동 해제 | 하지 않음(백엔드 토큰 폐기만) | 사용자가 명시적으로 로그아웃은 백엔드만 처리하도록 범위를 구분함 |
| 탈퇴 시 SDK 연동 해제 | `GoogleAuthService.disconnect()` / `KakaoAuthService.unlink()` 신규 추가 후 호출 | 사용자가 탈퇴에는 SDK 연동 해제 포함을 선택 — 재가입 시 계정 선택 창이 정상적으로 다시 뜨게 하기 위함 |
| 탈퇴 실패 처리 | 로컬 토큰 유지, 에러만 노출 | 서버-클라이언트 상태 불일치(계정은 남아있는데 로그아웃 화면으로 이동) 방지 |
| 탈퇴 UX 완성도 | MVP(확인 다이얼로그 → 즉시 처리) | 사용자가 MVP(권장안)를 선택 — 탈퇴 사유 선택/재인증은 후속 작업 |

### 6. 고려사항 및 위험요소

**기술적 위험**:
- SDK 연동 해제(`disconnect`/`unlink`) API는 네트워크 상태나 SDK 내부 세션 상태에 따라 실패할 수 있음 → 이미 서버 탈퇴가 완료된 이후이므로, 실패해도 재시도 로직 없이 로그만 남기고 정상적으로 탈퇴 흐름을 종료해야 함(사용자에게 "탈퇴 실패"로 잘못 보고하지 않도록 주의).
- `AuthInterceptor`의 401 재시도 로직이 탈퇴 요청에도 동일하게 적용됨 — accessToken 만료 상태에서 탈퇴를 시도하면 refresh 후 재시도가 자연스럽게 이뤄지므로 별도 처리 불필요(기존 인터셉터 재사용 확인 필요, 구현 단계에서 검증).
- 탈퇴 API가 404/409 등 예외 상태를 반환하는 케이스(예: 이미 탈퇴된 계정)에 대한 서버 쪽 에러 스펙이 아직 공유되지 않음 — 구현 단계에서 일반적인 `DioException` 처리로 우선 대응하고, 필요 시 에러 코드별 분기를 추가.

**비즈니스 위험**:
- 탈퇴는 되돌릴 수 없는 파괴적 액션이므로 확인 다이얼로그 문구에 "삭제 후 복구 불가"를 명확히 고지해야 함 — 법적/고객 문의 리스크 최소화.
- 탈퇴 유예기간(soft delete) 없이 즉시 하드 삭제하는 정책이 실제 서비스 정책과 일치하는지 백엔드/기획 측 재확인 필요(이번 작업 범위 밖이지만 후속 정책 변경 시 영향받는 지점으로 기록).

### 7. 성공 기준

- [ ] `AuthApi.withdraw()`가 `DELETE /api/users/me`를 호출하고 정상적으로 완료된다.
- [ ] 설정 화면에서 로그아웃 버튼 탭 시 기존과 동일하게 토큰 폐기 → 로컬 정리 → 로그인 화면 이동이 동작한다(홈 화면에는 더 이상 로그아웃 버튼이 없음).
- [ ] 설정 화면에서 탈퇴 버튼 탭 시 확인 다이얼로그 → 탈퇴 API 호출 → 성공 시 카카오/구글 SDK 연동 해제 + 로컬 토큰 삭제 + 로그인 화면 이동까지 한 흐름으로 동작한다.
- [ ] 탈퇴 API 실패 시 로컬 토큰이 삭제되지 않고 에러가 사용자에게 노출된다.
- [ ] 네트워크 오류/토큰 만료 등 예외 상황에서 앱이 크래시 없이 에러를 처리한다.
