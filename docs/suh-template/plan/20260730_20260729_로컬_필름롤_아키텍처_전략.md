# 🎯 이슈 #41 방향 전환 — 필름롤/코스/방문/사진 로컬 관리 전략 문서

관련 이슈: https://github.com/team-chaerok/chaerok-fe/issues/41
선행 문서: `docs/suh-template/analyze/20260730_20260729_관광지_조회_및_코스_추천_필름롤_분석.md` (API 기반 구조 분석 — 이번 문서로 방향이 대체됨)

## 1. 요약

관광지 목록·추천 코스는 기존처럼 백엔드 API(`PlacesApi`, `CoursesApi`)에서 조회하되, **필름롤/선택 코스/방문 상태/사진 메타데이터는 백엔드가 아니라 Flutter 앱의 로컬 저장소(Drift)에서 관리**하는 구조로 전환한다. 사진 원본은 앱 내부 파일 시스템에, DB에는 경로/메타데이터만 저장한다. 상태관리는 현재 프로젝트 방식(별도 라이브러리 없이 `StatefulWidget`+`setState`)을 그대로 유지한다.

## 2. 배경 및 목적

**문제/필요성**: 직전 분석(이슈 #41 초안)에서는 백엔드의 `Course`(ACTIVE/INACTIVE)를 필름롤 대용으로 쓰는 안을 검토했으나, 사용자 확인 결과 **필름롤/코스/방문/사진은 서버가 아닌 프론트 로컬 DB가 원본(source of truth)**이어야 한다는 요구로 방향이 바뀌었다. 이는 오프라인에서도 필름롤 조회·방문·촬영이 끊기지 않아야 한다는 제품 요구사항으로 이해된다.

**목표**: 공주시/부여군/서산시/예산군 4개 지역에 대해, 지역 진입 → 로컬 필름롤 조회/생성 → (API로 받은) 관광지·추천 코스 중 선택 → 선택 스냅샷 로컬 저장 → 방문 인증 → 사진 촬영/저장 → 진행률 갱신 → 완료까지 전 과정을 로컬 DB + 로컬 파일 시스템만으로 동작시킨다.

**범위**:
- 포함: `RegionCode`/정규화, Drift 스키마·DAO, Repository/UseCase 계층, 필름롤 생성/재사용/완료 로직, 코스 선택 스냅샷 저장, 방문 인증, 사진 촬영(`camera` 패키지)·저장·삭제, 진행률 계산, 앱 재시작 복구, mock 위치, 화면 연결, 테스트.
- 제외(백엔드 소관, 이 저장소 밖): 필름롤/코스/방문 데이터의 서버 저장·동기화. (`isSynced` 필드는 스키마에 남겨두되 이번 스코프에서는 항상 로컬 전용으로만 사용하고 실제 서버 동기화 로직은 구현하지 않는다 — TODO로 명시.)

**중요 (P1)**
- 코스 변경 정책: 방문/사진 기록이 있으면 변경 차단(안전 기본값), 없으면 교체 허용
- 필름 컬렉션 화면(진행중/완료 구분, 정렬)
- 삭제 정책(필름롤 삭제 시 연관 장소/사진/파일 함께 정리)

**선택 (P2)**
- 썸네일 실제 리사이즈(`image` 패키지) — 1차는 원본 경로를 썸네일 경로로 임시 대체하고 TODO로 남기는 것도 허용
- 서버 동기화(`isSynced`) — 이번 스코프 밖, 필드만 남김

## 5. 선택한 접근 방식 (사용자 확정 사항 반영)

### 5.1 로컬 DB: **Drift** 채택 확정

| 방식 | 장점 | 단점 | 채택 여부 |
|---|---|---|---|
| **Drift** | SQL 기반 type-safe, FK/Unique Index/트랜잭션/`watch()` 스트림 지원 → "지역별 진행중 1개" 제약과 원자적 findOrCreate 구현에 가장 적합 | build_runner 코드젝 최초 도입(빌드 시간 증가) | ✅ **채택** (사용자 확정) |
| sqflite | 코드젝 없음, 현재 수기 스타일과 유사 | Unique/트랜잭션을 전부 raw SQL로 직접 관리 → 동시성 버그 위험 | 미채택 |
| Isar | 설정 간단, 객체 저장 직관적 | 관계형 제약(1:N:N, 지역별 유니크) 표현이 약하고 공식 유지보수 불확실성 | 미채택 |

**이유**: `regionCode + status=inProgress` 유니크 제약, 필름롤-장소-사진 3단 관계, 트랜잭션 기반 원자적 `findOrCreate`/`selectCourse`/`completeVisit`가 전부 요구사항에 명시돼 있어 관계형 DB의 강점이 그대로 필요하다. `analysis_options.yaml`이 이미 `.g.dart`를 제외 처리하고 있어 코드젝 도입 마찰도 적다.

### 5.2 사진 촬영: **`camera` 패키지** 채택 확정

**이유**: 방문 장소별 커스텀 촬영 UX(장소명/가이드 오버레이 등, 스펙 12장 "필름롤" 컨셉상 촬영 화면 자체가 핵심 기능일 가능성)를 고려해 `image_picker`보다 `camera` 패키지로 인앱 커스텀 카메라 화면을 구현한다. 대신 권한 처리(`permission_handler`는 이미 있음)와 프리뷰 라이프사이클(앱 백그라운드 전환 시 컨트롤러 dispose) 관리가 추가로 필요하다.

| 패키지 | 용도 |

## 7. 로컬 스키마 초안 (Drift 테이블 설계 방향)

```
FilmRolls(id PK, regionCode, regionName, title, status,
          selectedCourseId, selectedCourseTitle,
          totalPlaceCount, visitedPlaceCount, photoCount,
          createdAt, updatedAt, completedAt)
  - INDEX: regionCode
  - 부분 유니크(애플리케이션 레벨 트랜잭션으로 보강): regionCode + status='inProgress'

FilmRollPlaces(id PK, filmRollId FK→FilmRolls.id,
               serverPlaceId, externalPlaceId,
               name, address, category, latitude, longitude, imageUrl,
               visitOrder, isVisited, visitedAt, photoCount)
  - INDEX: filmRollId

Photos(id PK, filmRollId FK→FilmRolls.id, filmRollPlaceId FK→FilmRollPlaces.id,
       originalPath, thumbnailPath, latitude, longitude, takenAt, isSynced)
  - INDEX: filmRollPlaceId
```

FK는 Drift의 `references()` + `onDelete: KeyAction.cascade`로 필름롤 삭제 시 장소/사진 레코드가 함께 삭제되도록 구성(실제 파일 삭제는 Repository에서 별도 처리 필요 — DB cascade는 파일 시스템까지 못 미침).

## 10. 고려사항 및 위험요소

**기술적 위험**
- Drift 최초 도입 → `sqlite3_flutter_libs`의 iOS/Android/시뮬레이터 빌드 설정 필요(특히 macOS 개발 환경에서 심볼 문제 가능) — 1단계에서 최소 스키마로 빌드 관통 여부 먼저 검증
- `camera` 패키지는 iOS `Info.plist`/Android `AndroidManifest.xml`에 카메라 권한 선언 추가 필요 (현재 위치 권한만 선언돼 있을 가능성 높음 — 확인 필요)
- 코스 변경 차단 정책은 TODO로 명시된 미확정 기획 — 사용자/기획 확인 전까지는 "차단"으로 하드코딩
