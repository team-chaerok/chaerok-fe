## 🎯 방문 인증 사진 경로를 상대 경로로 저장 — 전략 문서

### 1. 요약

방문 인증 사진의 원본/썸네일 파일 경로를 DB(`photos.original_path` / `photos.thumbnail_path`)에
**절대 경로**로 저장하고 있어, 앱 재설치·iOS Data 컨테이너 UUID 변경·백업 복원 이후
`File(oldAbsolutePath)` 접근이 전부 실패한다(`PathNotFoundException`). 개발 중 `flutter run`은
매번 재설치라 UUID가 계속 바뀌어 재현이 잦다. 저장 시 **문서 디렉터리 기준 상대 경로**만
DB에 남기고, 읽는 시점에 `getApplicationDocumentsDirectory()`와 join해 절대 경로로 복원한다.
기존 절대 경로 행은 스키마 v6 마이그레이션으로 상대 경로화하고, 읽기 시점에도 방어 로직을 둔다.
파일이 실제로 없을 때는 `Image.file`의 `errorBuilder`로 회색 슬롯 플레이스홀더를 노출한다.

### 2. 배경 및 목적

**문제/필요성**

- `LocalPhotoStorage.save()`가 `originalFile.path` / `thumbnailFile.path`
  (= `/var/mobile/Containers/Data/Application/{UUID}/Documents/film_rolls/...`)를 반환.
- `PhotoRepositoryImpl.savePhoto()`가 그 절대 경로를 `PhotosCompanion.insert`의
  `originalPath` / `thumbnailPath`에 그대로 저장.
- iOS는 앱 Data 컨테이너 절대 경로(`.../Application/{UUID}/`)가 재설치·OS 마이그레이션·백업
  복원 시 바뀐다. DB의 사진 레코드는 이전 UUID를 가리키고 실제 파일은 새 경로 아래에 있어
  접근이 모두 실패.
- 2차 문제: `active_film_roll_card.dart`의 `Image.file(File(thumbnailPaths[index]))`에
  `errorBuilder`가 없어 파일 로드 실패 시 붉은 예외 박스가 그대로 노출된다.

**목표**

- 앱 재설치·컨테이너 경로 변경·백업 복원 이후에도, 실제 파일이 남아 있는 한 사진이 정상 표시된다.
- 파일이 실제로 없을 때는 붉은 예외 대신 플레이스홀더를 보여준다.
- 기존에 절대 경로로 저장된 레코드도 마이그레이션으로 복구한다.

**범위**

- 포함: 저장 시 상대 경로화, 읽기 시 절대 경로 복원(+ 구버전 절대 경로 방어),
  스키마 v6 마이그레이션, `Image.file` `errorBuilder` 플레이스홀더, 관련 테스트.
- 제외: 파일이 없는 고아 DB 행 정리 루틴(별도 이슈로). 서버 동기화(`isSynced`, `#41`) 무관.
  원격 사진(`FilmRollPhotoResponse` 등 `lib/data/`) 무관.

### 3. 요구사항

**필수 (P0)**

- `LocalPhotoStorage.save()`는 문서 디렉터리 기준 상대 경로를 반환한다:
  `film_rolls/{filmRollId}/{filmRollPlaceId}/original|thumbnail/{photoId}.jpg`
- DB `photos.original_path` / `photos.thumbnail_path`에는 상대 경로만 저장된다.
- 읽기 시점(`PhotoRepositoryImpl.findByPlace` / `findByFilmRoll` / `savePhoto` 반환 엔티티)에
  절대 경로로 복원되어, 기존 소비자(`FilmRollPhoto.originalPath` / `thumbnailPath` 사용처)는
  변경 없이 동작한다.
- 스키마 v6: 기존 절대 경로 행을 `film_rolls/` 이후 상대 경로로 재작성. 이미 상대 경로인 행은
  무변경(idempotent).
- 읽기 시점 방어: 저장값이 절대 경로여도 `film_rolls/`부터 잘라 복원(마이그레이션 누락·경합 대비).
- `active_film_roll_card.dart`의 `Image.file`에 `errorBuilder` 추가 → 파일 없음/디코드 실패 시
  회색 슬롯 플레이스홀더(예외 박스 미노출).

**중요 (P1)**

- `LocalPhotoStorage.delete()`는 입력 경로가 상대/구버전 절대 어느 쪽이든 처리한다
  (내부에서 복원 후 삭제).
- 회색 슬롯 플레이스홀더 모양을 기존 `_CapturedPhotoPlaceholderRow`와 공유(중복 제거).
- 신규 로직에 대한 단위/위젯 테스트, 마이그레이션 테스트.

**선택 (P2)**

- (제외됨) 파일이 없는 photos 레코드를 DB에서 제거하는 고아 행 정리 루틴.

### 4. 선택한 접근 방식

**방식**: DB에는 상대 경로만 저장하고, 읽기 시점(repository 계층)에서 절대 경로로 복원한다.
`LocalPhotoStorage`에 `resolve(String storedPath)` 헬퍼를 두어 저장/삭제/복원의 경로 규칙을
한 곳에 모은다. 도메인 엔티티(`FilmRollPhoto`)와 매퍼(`PhotoMapper`)는 인터페이스를 유지한다
(엔티티는 계속 절대 경로를 노출, 매퍼는 순수 매핑). 기존 데이터는 스키마 v6 `onUpgrade`에서
SQLite 문자열 함수(`instr` + `substr`)로 재작성하고, `resolve()`에도 구버전 절대 경로 방어를 둔다.

**이유**

- 절대 경로가 DB에 남지 않으므로 컨테이너 UUID 변경에 근본적으로 영향받지 않는다.
- 복원을 repository 계층 한 곳에 두면 소비자(홈 대시보드 등)와 도메인 계층은 그대로다.
- 경로 규칙(저장 형식, `film_rolls/` 마커, 복원)을 `LocalPhotoStorage` 한 파일에 응집.
- 마이그레이션 + 읽기 방어(defense-in-depth)로, 마이그레이션이 어떤 이유로 누락돼도
  화면이 깨지지 않는다.
- 기존 테스트가 이미 `PathProviderPlatform.instance`를 `_FakePathProviderPlatform`으로
  갈아끼우는 패턴을 쓰므로, `LocalPhotoStorage`의 `const` 싱글턴 구조를 바꾸지 않아도 테스트 가능.

**대안**

- *엔티티가 상대 경로를 보유하고 위젯이 복원*: 모든 소비자와 위젯이 async 복원을 알아야 하고,
  `Image.file` 호출부마다 `FutureBuilder`가 필요해 변경 범위가 크다. 채택 안 함.
- *매퍼(`toEntity`)를 async로 만들어 복원*: 매퍼가 `path_provider`에 의존하게 되고
  `List.map` 대신 `Future.wait`가 필요. 도메인 매핑 계층에 IO 의존을 넣는 건 부적절. 채택 안 함.
- *마이그레이션 없이 읽기 시 정규화만*: DB가 계속 절대/상대 혼재 상태로 남아 "source of truth"가
  흐려진다. 읽기 방어는 유지하되 마이그레이션도 함께 수행(사용자 결정). 채택 안 함(단독으로는).
- *문서 디렉터리 경로를 static 캐시*: 테스트가 매번 다른 temp dir로 `PathProviderPlatform`을
  교체하므로 캐시가 오염된다. 캐시 없이 매 조회 시 `getApplicationDocumentsDirectory()` 호출
  (리스트 로드 시점에만 발생, 비용 미미). 채택 안 함.

### 5. 주요 결정사항

| 결정 | 선택 | 이유 |
|------|------|------|
| DB 저장 형식 | 문서 디렉터리 기준 상대 경로 (`film_rolls/...`) | 컨테이너 UUID 변경에 불변 |
| 절대 경로 복원 위치 | `PhotoRepositoryImpl` (읽기·저장 반환·삭제 진입점) | 소비자/도메인 계층 무변경 |
| 경로 규칙 소유 | `LocalPhotoStorage` (`save` 반환 + `resolve` + `delete`) | 규칙 응집, 단일 책임 |
| 매퍼(`PhotoMapper`) | 순수 매핑 유지 (상대 in → 상대 out) | IO 의존 배제, 테스트 용이 |
| 기존 데이터 | 스키마 v6 마이그레이션 + 읽기 시 방어 | 근본 수정 + defense-in-depth |
| 마이그레이션 방식 | `UPDATE ... SET x = substr(x, instr(x, 'film_rolls/')) WHERE instr(x, 'film_rolls/') > 0` | 상대 경로 행은 무변경(idempotent), 순수 SQL |
| 파일 없음 UI | `errorBuilder` → 회색 슬롯 (`_CapturedPhotoPlaceholderRow` 스타일 공유) | 기존 디자인 일관성 (사용자 결정) |
| 고아 DB 행 정리 | 이번 범위 제외 | 별도 이슈 (사용자 결정) |
| `LocalPhotoStorage` 구조 | `const` 싱글턴 유지 | 기존 DI/테스트 패턴 보존 |

### 6. 고려사항 및 위험요소

**기술적 위험**

- *Drift 컬럼명 매핑*: 코드의 `originalPath` → 실제 컬럼 `original_path` (Drift 기본 snake_case).
  마이그레이션 SQL은 실제 컬럼명 사용. → `local_database.g.dart` 또는 실 DB 스키마로 컬럼명 확인 후 작성.
- *`p.relative` vs 문자열 절단 불일치*: `save()`는 `p.relative(file.path, from: docs.path)`로
  상대화하고, `resolve()`의 구버전 방어는 `film_rolls/` 마커 기준 절단. 두 결과가
  동일 형식(`film_rolls/...`, 구분자 `/`)이 되도록 통일. iOS/Android 모두 `/` 구분자라 문제 없음.
- *마이그레이션 idempotency*: `instr(x, 'film_rolls/')`가 1을 반환하는 상대 경로 행에
  `substr(x, 1)` = 원본 그대로. `film_rolls/`를 포함하지 않는 예외 값은 `WHERE` 절로 건너뜀. 안전.
- *`errorBuilder` 발화 타이밍*: `Image.file` 에러는 비동기 디코드 실패 시 발생. 위젯 테스트에서
  `pumpAndSettle`로 안정화하거나, 플레이스홀더 위젯 존재를 `find`로 검증. 과하게 정밀한
  픽셀 검증은 피함.
- *마이그레이션 테스트 하네스 무게*: drift `schema` 마이그레이션 테스트 도구가 무거우면,
  v5 DB에 절대 경로 행을 직접 삽입 → v6 오픈 → 행 값 검증하는 경량 통합 테스트로 대체.
- *기존 테스트 영향*: `photoStorage: LocalPhotoStorage.instance`를 쓰는 다수 테스트가 있으나
  `save()` 반환 형식 변경은 대부분 경로 문자열을 직접 단언하지 않아 영향이 적을 것으로 예상.
  전체 `flutter test` 회귀 확인 필요.

**비즈니스 위험**

- *이미 재설치로 실제 파일이 사라진 사용자*: 마이그레이션으로 경로는 상대화되지만 파일 자체가
  없으면 여전히 표시 불가. 이 경우 `errorBuilder` 회색 슬롯으로 그레이스풀하게 처리(예외 미노출).
  근본 복구는 불가능(원본 유실) — 예상 동작에 부합.
- *배포 후 롤백 시나리오*: v6로 올라간 뒤 구버전 앱으로 되돌리면, 구버전은 상대 경로를
  절대 경로로 취급해 파일을 못 찾음. 일반적 롤백 정책상 허용 범위로 판단(스키마 다운그레이드는
  원래 미지원).

### 7. 성공 기준

- [ ] `LocalPhotoStorage.save()`가 `/`로 시작하지 않는 상대 경로(`film_rolls/...`)를 반환한다.
- [ ] `savePhoto()` 후 `photos.original_path` / `thumbnail_path` 행 값이 상대 경로다.
- [ ] `findByPlace()` / `findByFilmRoll()`가 반환한 엔티티의 경로로 `File(...).existsSync()`가 true다
      (실제 파일이 있을 때).
- [ ] `resolve()`가 구버전 절대 경로(`/var/.../Application/{UUID}/Documents/film_rolls/a/b/thumbnail/c.jpg`)를
      현재 문서 디렉터리 기준 절대 경로로 재결합한다.
- [ ] v5 DB의 절대 경로 photo 행이 v6 오픈 후 상대 경로로 재작성된다. 이미 상대 경로인 행은 불변.
- [ ] 존재하지 않는 경로로 `_CapturedPhotoRow`를 렌더해도 예외 박스 없이 회색 슬롯이 표시된다.
- [ ] `flutter analyze` 무경고, `flutter test` 전체 통과.
