## 🎯 토큰 저장 및 관리 로직 설계 전략 문서

### 1. 요약

로그인/회원가입 API가 발급하는 `accessToken`/`refreshToken`이 현재 어디에도 저장되지 않아, 발급 직후부터 인증이 사실상 동작하지 않는 상태다. 이미 프로젝트에 있는 `flutter_secure_storage`를 그대로 활용해 토큰 저장을 담당하는 공용 서비스(`TokenStorage`)를 만들고, 로그인/회원가입 화면에서 명시적으로 저장을 호출하도록 한다. 동시에 로그인 여부를 앱 전역에서 구독할 수 있는 최소한의 반응형 상태(`AuthState`)를 도입해, 향후 자동 로그인·로그아웃 라우팅 작업이 이 위에 바로 얹힐 수 있게 한다.

### 2. 배경 및 목적

**문제/필요성**:
- `AuthApi.signUp`, `AuthApi.login`이 반환하는 `TokenResponse`가 `signup_screen.dart`, `login_screen.dart`에서 그대로 버려짐 — 저장 호출이 아예 없음.
- `AuthInterceptor`(`lib/core/network/interceptors/auth_interceptor.dart`)는 매 요청마다 `FlutterSecureStorage`에서 토큰을 읽지만, 그 storage 인스턴스는 `DioClient` 생성자 내부에 비공개로 존재해 화면 코드가 접근할 방법이 없음.
- 결과적으로 로그인/회원가입 직후 모든 인증 필요 API 호출에 `Authorization` 헤더가 붙지 않고, 401 시 refresh도 refreshToken이 없어 항상 실패함.
- `DioClient.init(onUnauthorized: ...)` 콜백 훅은 이미 있으나 실제로 아무도 등록/소비하지 않음 — 로그인 상태 변화를 앱이 알 방법이 없음.

**목표**:
- 토큰을 안전하게 저장/조회/삭제하는 공용 서비스를 도입하고, 발급 시점(로그인/회원가입 성공 응답)에 명시적으로 저장하도록 연결한다.
- 로그인 여부를 외부에서 구독 가능한 최소 반응형 상태로 노출해, 이후 자동 로그인·로그아웃 UI 작업이 별도 인프라 변경 없이 진행될 수 있게 한다.

**범위**:
- 포함: 토큰 저장/조회/삭제 서비스 설계, `AuthInterceptor`/`DioClient`와의 통합, 로그인/회원가입 화면의 명시적 저장 호출, 로그인 상태 반응형 노출(`ValueNotifier` 수준).
- 제외(별도 작업): 스플래시 자동 로그인 라우팅, 로그아웃 버튼/화면 UI, `AuthApi.logout` 실제 호출 흐름.

### 3. 요구사항

**필수 (P0)**:
- 로그인/회원가입 성공 시 accessToken/refreshToken을 안전 저장소에 저장한다.
- `AuthInterceptor`가 기존과 동일하게 저장된 토큰을 읽어 요청 헤더에 붙이고, refresh 성공 시 갱신된 토큰을 다시 저장한다 (기존 동작 유지, 저장소만 공용화).
- 토큰 삭제(clear) API를 제공해 refresh 실패 시 기존처럼 두 토큰을 모두 지운다.

**중요 (P1)**:
- 로그인 여부를 외부에서 구독할 수 있는 반응형 상태(`ValueNotifier<bool>` 등)를 제공해, 토큰 저장/삭제 시 자동으로 갱신되게 한다.
- `DioClient`의 기존 `onUnauthorized` 콜백이 이 반응형 상태 갱신과 자연스럽게 연결되도록 구조를 잡는다 (실제 라우팅 연결은 이번 범위 밖).

**선택 (P2)**:
- 앱 시작 시점에 저장된 토큰 유무를 조회하는 헬퍼(`hasValidSession` 등) — 다음 단계인 자동 로그인 작업에서 바로 재사용 가능하도록 미리 인터페이스만 열어둠.

### 4. 선택한 접근 방식

**방식**: 기존 `flutter_secure_storage`를 그대로 사용하되, `DioClient` 내부에 갇혀 있던 storage 인스턴스를 `TokenStorage`라는 단일 서비스 클래스로 추출한다. 화면(Login/Signup)은 API 응답을 받은 직후 `TokenStorage.saveTokens(...)`를 명시적으로 호출한다. 로그인 상태는 `TokenStorage` 내부의 `ValueNotifier<bool> isLoggedIn`으로 노출하고, 저장/삭제 시점에 자동 갱신한다.

**이유**:
- 패키지 선택 자체는 이미 끝나 있음 — `flutter_secure_storage`가 pubspec에 있고 `AuthInterceptor`가 이미 이걸로 암호화 저장(Android `encryptedSharedPreferences`, iOS Keychain `first_unlock`)을 하고 있어 일관성을 유지하는 것이 맞음. 토큰처럼 민감한 값을 `shared_preferences`(평문)로 옮길 이유가 없음.
- "화면에서 명시적으로 저장" 방식은 데이터 흐름이 코드만 보고 추적 가능하고(어디서 저장되는지 인터셉터 내부를 뒤질 필요 없음), 단위 테스트 시 `TokenStorage`를 mock하기 쉬움.
- `ValueNotifier`는 프로젝트에 Provider/Riverpod 등 상태관리 패키지가 전혀 없는 현재 구조에서 새 의존성 추가 없이 반응형 구독을 제공하는 가장 가벼운 선택.

**대안 (왜 선택하지 않았는지)**:
- **DioClient가 응답을 가로채 자동 저장**: 화면 코드는 더 짧아지지만, "로그인 성공"과 "회원가입 성공"의 응답 구조가 서로 달라(`OAuthLoginResponse.tokens`는 nullable, `TokenResponse`는 signup에서 바로 옴) 인터셉터가 분기 처리를 떠안게 되어 오히려 암묵적이고 디버깅이 어려워짐. 사용자가 명시적 저장 방식을 선택함.
- **shared_preferences**: 평문 저장이라 accessToken/refreshToken 같은 민감 정보에 부적합. 이미 flutter_secure_storage가 쓰이고 있어 굳이 다른 저장소를 병행할 이유 없음.
- **Riverpod/Provider 도입**: 로그인 상태 하나를 위해 새 패키지와 앱 전체 구조 변경(ProviderScope 등)을 끌어오는 건 이번 범위(저장/관리 로직)에 비해 과함. 나중에 상태관리가 프로젝트 전반에 필요해지면 그때 마이그레이션.

### 5. 주요 결정사항

| 결정 | 선택 | 이유 |
|------|------|------|
| 저장 패키지 | `flutter_secure_storage` (기존 유지) | 이미 도입되어 있고 플랫폼별 암호화 옵션이 설정된 상태 — 새 패키지 도입 불필요 |
| 서비스 위치 | `lib/core/network/token_storage.dart` (가칭) | `AuthInterceptor`/`DioClient`와 같은 계층에서 인증 인프라로 취급 |
| 저장 시점 | Login/Signup 화면에서 API 응답 직후 명시적 호출 | 데이터 흐름 추적 용이, 사용자 선택 반영 |
| 상태 노출 방식 | `ValueNotifier<bool>` (TokenStorage 내부) | 새 패키지 없이 최소 반응형 제공, 추후 라우팅 작업에서 바로 소비 가능 |
| DioClient 통합 | `DioClient`가 `TokenStorage` 싱글톤을 받아 `AuthInterceptor`에 주입 | 기존 인터셉터 로직(read/write/delete) 재사용, 중복 storage 인스턴스 제거 |
| 로그아웃/자동 로그인 라우팅 | 이번 범위에서 제외 | 사용자가 저장/관리 로직만으로 범위 확정, 후속 작업으로 분리 |

### 6. 고려사항 및 위험요소

**기술적 위험**:
- `TokenStorage`를 싱글톤으로 추출하면서 `DioClient`와 `AuthInterceptor` 생성 순서/의존성이 바뀜 — `DioClient.init()`을 먼저 호출해야 하는 기존 제약(주석에 명시됨)이 깨지지 않는지 확인 필요. → 구현 단계에서 `AppStartup.initialize()` 흐름을 그대로 유지하며 `TokenStorage`를 `DioClient`보다 먼저 생성하는 순서로 배치.
- 화면에서 명시적으로 저장하는 방식이라, 저장 호출을 빠뜨리는 새 로그인 경로(예: 추후 추가되는 소셜 로그인)가 생기면 다시 같은 문제가 재발할 수 있음. → 코드 리뷰 시 "토큰 발급 API 호출부는 반드시 TokenStorage.saveTokens 페어링" 체크리스트화 권장.
- `ValueNotifier`를 누가 dispose하는지 애매해질 수 있음(싱글톬이라 앱 생명주기 동안 유지되므로 dispose 불필요하지만 테스트 코드에서 인스턴스를 새로 만들 경우 주의).

**비즈니스 위험**:
- 없음 — 사용자 대면 동작 변화 없이 내부 인증 배선만 고치는 작업.

### 7. 성공 기준

- [ ] 로그인/회원가입 성공 시 accessToken/refreshToken이 `TokenStorage`를 통해 저장된다.
- [ ] `AuthInterceptor`가 공용 `TokenStorage`를 통해 기존과 동일하게 요청 헤더 부착 및 401 refresh 동작을 수행한다.
- [ ] 로그인 상태를 앱 어디서나 `TokenStorage.isLoggedIn`(ValueNotifier)으로 구독할 수 있다.
- [ ] `AuthApi.logout` 호출 흐름, 스플래시 자동 로그인 라우팅은 이번 범위에 포함하지 않고 후속 작업으로 명시적으로 분리된다.
