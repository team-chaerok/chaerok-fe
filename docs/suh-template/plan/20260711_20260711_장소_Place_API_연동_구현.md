## 🎯 장소(Place) API 연동 전략 문서

### 1. 요약

`lib/data/remote/`에는 `auth_api.dart`, `users_api.dart`, `health_api.dart`만 있고 장소(Place) 관련 API 호출부가 없다. `lib/data/models/`에도 장소 응답 모델이 없어 지역별 장소 조회 기능을 붙일 수 없다. 실제 백엔드 Swagger 스펙을 확인한 결과, `/api/places`(목록), `/api/places/{placeId}`(상세), `/api/places/search`(검색), `/api/places/external`(TourAPI 실시간 조회) 4개 엔드포인트가 모두 페이지네이션 없는 **순수 JSON 배열/객체**를 반환한다. 이번 작업은 이 스펙에 정확히 맞춘 `PlaceListResponse`, `PlaceDetailResponse`, `PlaceSearchResponse` 3개 모델과, `AuthApi`/`UsersApi`와 동일한 정적 메서드 패턴의 `PlacesApi`를 신설해 4개 GET 요청을 연동한다.

### 2. 배경 및 목적

**문제/필요성**:
- `lib/data/remote/`에 장소 조회를 담당하는 API 클래스가 전혀 없어 지역별 장소 조회 기능(홈 화면 추천, 장소 목록/상세, 검색)을 구현할 수 없는 상태.
- 지역 정보(`region_response.dart`)는 이미 있지만, 실제 "장소" 데이터를 가져오는 연동은 아직 없음 — 지역 선택 이후 흐름이 끊겨 있음.
- `docs/project-structure.md`에는 `features/place/` 하위에 repository/controller까지 포함한 아키텍처가 문서화되어 있으나, 이는 아직 구현되지 않은 목표 구조이고 현재 실제 코드(`auth_api.dart`, `users_api.dart`)는 `data/remote/` + `data/models/`의 단순 정적 클래스 패턴을 쓰고 있음. 이번 작업은 이슈에서 명시한 대로 **현재 실제 패턴**을 따른다 (repository 계층은 범위 밖).

**목표**:
- Swagger 스펙과 1:1로 일치하는 `PlaceListResponse`, `PlaceDetailResponse`, `PlaceSearchResponse` 모델 작성.
- `PlacesApi` 클래스를 신설해 4개 GET 엔드포인트를 `AuthApi`/`UsersApi`와 동일한 코드 스타일(`DioClient.instance.get<T>` + `fromJson`)로 연동.

**범위**:
- 포함: 모델 3개, `PlacesApi` 4개 메서드, 각 메서드의 쿼리/경로 파라미터 처리.
- 제외(별도 작업): `features/place/` 화면·위젯·컨트롤러·repository 계층, 카테고리(enum) 필터 UI, 검색 결과 캐싱/페이지네이션(백엔드 스펙상 현재 없음), 지도 마커 연동.

### 3. 요구사항

**필수 (P0)**:
- `PlaceListResponse` — `id, tourContentId, kakaoPlaceId, title, address, latitude, longitude, firstImageUrl, categoryGroup, categoryDetail, isRepresentative, source` 필드, Swagger 예시 JSON을 오류 없이 파싱.
- `PlaceDetailResponse` — 위 필드 + `regionId, overview, lDongRegnCd, lDongSignguCd, lclsSystm1, lclsSystm2, lclsSystm3` 추가 필드.
- `PlaceSearchResponse` — `PlaceListResponse`와 동일하나 `isRepresentative` 필드가 없음.
- `PlacesApi.getPlaces(int regionId)` — `GET /api/places?regionId=`, `List<PlaceListResponse>` 반환.
- `PlacesApi.getPlaceDetail(int placeId)` — `GET /api/places/{placeId}`, `PlaceDetailResponse` 반환.
- `PlacesApi.searchPlaces({required int regionId, required String keyword})` — `GET /api/places/search?regionId=&keyword=`, `List<PlaceSearchResponse>` 반환.
- `PlacesApi.getExternalPlaces(int regionId)` — `GET /api/places/external?regionId=`, `List<PlaceListResponse>` 반환 (스키마가 `PlaceListResponse`와 완전히 동일해 별도 모델 만들지 않고 재사용).

**중요 (P1)**:
- 배열 응답 파싱은 `DioClient.get`의 `fromJson: (data) => (data as List).map(...).toList()` 형태로 처리 — 기존 코드베이스에 배열 응답 처리 선례가 없으므로 이번에 패턴을 확립.
- `null` 가능성이 있는 필드(`tourContentId`, `kakaoPlaceId`, `firstImageUrl`, `overview` 등)는 방어적으로 nullable로 선언.

**선택 (P2)**:
- `categoryGroup`/`categoryDetail`/`source`의 Dart enum화(현재는 `String`으로 1차 처리).

### 4. 선택한 접근 방식

**모델 구조 — 방식 A(선택): Swagger 스키마 1:1 대응, 상속 없는 독립 플랫 클래스 3개**
- `region_response.dart`, `token_response.dart` 등 기존 모델과 동일하게 상속/믹스인 없이 각 클래스가 자기 필드를 직접 선언.
- **대안(방식 B, 미선택)**: 공통 `PlaceCore` 베이스 클래스를 두고 3개 모델이 상속/컴포지션으로 필드를 공유. 필드 중복은 줄지만, `PlaceListResponse`엔 있고 `PlaceSearchResponse`엔 없는 `isRepresentative` 같은 차이 때문에 베이스 클래스 설계가 오히려 복잡해지고, 기존 코드베이스 어디에도 모델 상속 패턴이 없어 일관성이 깨짐. 채택하지 않음.

**API 계층 — 방식 A(선택): `AuthApi`/`UsersApi`와 동일한 정적 메서드 클래스**
- `PlacesApi._()` private 생성자 + `static Future<...>` 메서드 4개, `DioClient.instance.get<T>` 직접 호출.
- **대안(방식 B, 미선택)**: `docs/project-structure.md`가 그리는 `place_repository.dart` 같은 repository 추상화를 지금 도입. 이슈에서 명시적으로 "UsersApi, AuthApi와 동일한 패턴"을 요구했고, 현재 auth/users 쪽에도 아직 repository 계층이 없어 place만 먼저 도입하면 오히려 비일관성이 생김. 채택하지 않음(향후 전체 feature에 repository 계층을 도입할 때 함께 처리).

### 5. 주요 결정사항

| 결정 | 선택 | 이유 |
|---|---|---|
| 페이지네이션 | 미포함, 배열 그대로 반환 | Swagger 스펙 확인 결과 4개 엔드포인트 모두 `totalCount`/`page` 없는 순수 JSON 배열(상세는 단일 객체) |
| 모델 재사용 범위 | List/Detail/Search 3개 개별 클래스 + External은 List 재사용 | External 스키마가 List와 필드 완전 일치(`isRepresentative` 포함), Search는 `isRepresentative` 없음, Detail은 필드가 대폭 추가 — 억지로 공통 베이스를 두면 null 처리만 복잡해짐 |
| `getPlaces()` 파라미터 | `regionId`(필수, `int`) | 이슈 설명엔 파라미터 언급이 없었으나, Swagger에 `regionId` query 파라미터가 필수로 명시됨 |
| `categoryGroup`/`categoryDetail`/`source` 타입 | 1차 `String` | Swagger가 enum 전체 값을 명시하지 않음 — enum으로 고정 시 백엔드가 새 값을 추가하면 파싱 실패 위험. 카테고리 필터 UI를 붙이는 시점에 enum으로 승격 |
| nullable 필드 처리 | `tourContentId`/`kakaoPlaceId`/`firstImageUrl`/`overview` 등은 `String?` | `source`(TOUR_API/KAKAO 등)에 따라 두 ID 중 하나만 채워질 가능성이 높고 이미지·개요도 없을 수 있음 — 방어적 null-safety |
| 빈/실패 응답 처리 | 리스트는 `response.data ?? const []`, 상세는 `PlaceDetailResponse.empty()` | 기존 `AuthApi`의 `TokenResponse.empty()` 패턴과 일관성 유지 |

### 6. 고려사항 및 위험요소

**기술적 위험**:
- Swagger에 각 필드의 nullable 여부가 명시되어 있지 않음 — 방어적으로 nullable 처리했지만, 실제 응답에서 예상과 다른 `null`이 나오면 파싱 예외 가능. 구현 후 실제 백엔드(또는 스테이징) 호출로 검증 필요.
- `categoryGroup`/`categoryDetail`/`source`를 `String`으로 느슨하게 받으므로, 이후 카테고리별 아이콘/필터 매핑 시 오타로 인한 매칭 실패 위험 — enum 승격 시점에 값 목록을 백엔드와 재확인 필요.

**비즈니스 위험**:
- `searchPlaces`는 백엔드가 TourAPI 우선 호출 후 부족하면 Kakao Local API로 보완하는 구조라 응답 지연 가능성이 있음 — 별도 타임아웃 조정 없이 기존 `DioClient` 공통 설정(connectTimeout 10s, receiveTimeout 30s)을 그대로 적용하며, 체감 지연이 문제되면 후속 작업으로 로딩 UX를 보완.
