- 브랜치: `20260904_#71_가고_싶은_장소로_커스텀_코스_만들어_필름롤_시작`

## 1. 요약

`CourseSelectionScreen`은 현재 `CoursesApi.getRecommendedCourses`가 내려준 추천 코스 중 하나만 고를 수 있고, "가고 싶은 곳을 직접 골라 코스를 만드는" 경로가 없다. 백엔드는 이미 `POST /api/courses`(직접 만들기), `POST /api/courses/active/places`(장소 추가), `GET /api/courses/active`(현재 ACTIVE 코스 조회)를 제공하지만 앱에서 호출하지 않고, 탐색 모드의 북마크 기능도 코스로 이어지지 않아 사실상 죽은 기능이다. 이번 작업은 코스 선택 화면에 "직접 만들기" 모드를 추가해 관광지 목록·검색·북마크 3개 장소 소스를 통합한 피커로 1~3개 장소를 고르고, 서버에 ACTIVE 코스로 생성한 뒤 기존 필름롤 코스 확정 흐름에 연결한다.

## 2. 배경 및 목적

**문제/필요성**
- 추천 코스만 존재 → "원하는 장소로 직접 만들고 싶다"는 기본 시나리오가 막혀 있음.
- 탐색 모드 북마크(`BookmarkStore`, SharedPreferences 로컬 전용)가 코스로 전환되지 않아 죽은 기능.
- 백엔드 API(`createCourse`/`addActiveCoursePlaces`/`getActiveCourse`)는 준비돼 있지만 미사용.

**목표**
- 코스 선택 화면에서 추천/직접 만들기를 오가며, 관광지 목록·장소 검색·북마크 장소를 한 곳에서 골라 1~3개 코스를 구성하고 확정할 수 있게 한다.
- 확정된 커스텀 코스를 기존 "코스 선택 완료 → 필름롤 반영" 흐름과 동일하게 동작시킨다.

**범위**
- 포함: 코스 선택 화면 2-모드화, 장소 피커(관광지 목록+검색+북마크 통합, 1~3개 선택/순서 지정), `createCourse` 연동, 커스텀 코스 → 필름롤 확정 연결, 3개 초과 방지, 기존 ACTIVE 코스 대체 확인, 북마크 화면 진입점.
- 제외(이번 이슈 범위 밖): `addActiveCoursePlaces`(장소 추가 API)와 `getActiveCourse`(ACTIVE 코스 조회) 활용은 코스 "생성" 흐름에 필요한 범위까지만 다루고, 별도의 "코스 관리(장소 추가/재편집)" UI는 포함하지 않는다. 북마크의 서버 동기화도 범위 밖(로컬 전용 유지).

## 3. 요구사항

**필수 (P0)**
- 코스 선택 화면에 추천/직접 만들기 탭(또는 토글) 추가, 기존 추천 흐름은 그대로 유지.
- 장소 피커: 관광지 목록(`PlacesApi.getPlaces`) + 검색(`PlacesApi.searchPlaces`) + 북마크(`BookmarkStore`) 통합, 1~3개 선택 및 순서 지정.
- 확정 시 `CoursesApi.createCourse` 호출 → `SelectedCourseResponse` 획득 → 필름롤 코스 확정 흐름 재사용.
- 3개 초과 선택 방지 UI.
- 기존 ACTIVE 코스가 있는 상태에서 새로 만들면 "기존에 만든 코스를 대체합니다" 확인 노출(서버가 INACTIVE 처리 후 재생성).
- 북마크 화면/오버레이에 "이 장소로 코스 만들기" 진입점 추가.

**중요 (P1)**
- `BookmarkedPlace` 모델에 `categoryGroup`/`source`/`placeId`(또는 `externalPlaceId`) 필드 보강 — 커스텀 코스 생성 시 서버 전송 필드(`CoursePlaceSaveRequest`)를 채우기 위해 필요.
- 커스텀 코스 확정 전용 유스케이스(`SelectCustomCourseUseCase` 등) 신규 작성, `FilmRollController`에 대응 메서드 추가.
- `CourseSelectionScreen`을 사용하는 3개 호출부(`film_roll_screen.dart`, `film_roll_entry_flow.dart`의 `pushCourseSelectionAndConfirm`, `film_roll_progress_view.dart`) 모두 "추천 코스 선택"과 "커스텀 코스 확정" 두 결과를 구분해 처리하도록 정리.

**선택 (P2)**
- 기존 `BookmarkedPlace` 로컬 저장 데이터(필드 보강 이전에 저장된 항목) 마이그레이션/방어 처리.
- 피커 내 지도 미리보기(기존 `_CourseMapPreviewSheet`/`CourseMapView` 재사용 가능성 검토).

## 4. 선택한 접근 방식

**방식**: 코스 선택 화면(`CourseSelectionScreen`) 내부에 탭/토글로 "추천" / "직접 만들기" 두 모드를 통합하고, 장소 소스 3종(관광지 목록·검색·북마크)을 처음부터 함께 지원한다. 코스 확정 로직은 기존 `SelectCourseUseCase`를 건드리지 않고 커스텀 코스 전용 유스케이스를 신설해 연결한다. 북마크 필드는 `BookmarkedPlace` 모델을 확장해 원본 데이터를 보강한다.

**이유**
- 화면 통합: 진입점이 `FilmRollScreen`/`FilmRollEntryFlow`/`FilmRollProgressView` 3곳이라 별도 화면을 새로 만들면 3곳 모두 신규 라우팅을 추가해야 하지만, 기존 화면 내 탭 전환이면 push 지점 변경이 최소화된다.
- 장소 소스 3종 동시 지원: 이슈 본문이 3종 통합을 요구사항으로 명시했고, 나중에 부분적으로 추가하면 피커 UI를 다시 설계해야 할 가능성이 큼.
- 커스텀 전용 유스케이스 신설: `SelectCourseUseCase`는 추천 코스(`CourseResponse`, 장소 구성으로 합성한 문자열 `courseId`)를 전제로 하고, `CourseCandidatePlace.fromCoursePlaceResponse`는 `CoursePlaceResponse`의 위도/경도를 필수로 요구한다. 반면 `createCourse`가 반환하는 `SelectedCourseResponse`/`SelectedCoursePlaceResponse`에는 위도/경도가 없다. 기존 유스케이스에 어댑터를 씌우면 없는 좌표를 억지로 채우거나 놓치는 위험이 생기므로, 사용자가 이미 좌표를 들고 있는 원본 선택 장소로 `CourseCandidatePlace`를 직접 구성하고 서버 응답의 `courseId`(int→String)만 가져다 쓰는 별도 유스케이스가 더 안전하다.
- `BookmarkedPlace` 확장: identityKey로 재조회하는 대안은 검색 결과로 얻은 장소(서버 DB 미저장)가 재조회 시 사라지거나 값이 달라질 수 있어 신뢰성이 떨어진다.

**대안 (왜 선택하지 않았는지)**
- 북마크만 우선 지원 → 이슈가 요구하는 "관광지 목록+검색" 경로가 빠져 요구사항 미충족.
- 별도 화면 분리 → 네비게이션 지점이 3곳이라 변경 범위가 오히려 커짐.
- identityKey 재조회로 북마크 필드 보강 → API 호출 증가, 검색 전용 장소의 재조회 실패 가능성.
- 기존 `SelectCourseUseCase` 어댑터 재사용 → 좌표 필드 부재를 우회하는 방식이 되어 데이터 정합성 리스크가 큼.

## 5. 주요 결정사항

| 결정 | 선택 | 이유 |
|------|------|------|
| 장소 소스 범위 | 관광지 목록 + 검색 + 북마크 3종 동시 지원 | 이슈 요구사항 100% 충족, 재작업 방지 |
| 화면 구조 | `CourseSelectionScreen` 내 탭/토글로 통합 | 호출부 3곳의 변경 범위 최소화 |
| 북마크 필드 부족 | `BookmarkedPlace` 모델에 `categoryGroup`/`source`/`placeId` 등 보강 | 재조회보다 안정적, API 호출 절감 |
| 코스 확정 연결 | `SelectCustomCourseUseCase` 신규 작성 | `SelectedCourseResponse`에 좌표가 없어 기존 유스케이스 재사용 시 좌표 손실 위험 |

## 6. 고려사항 및 위험요소

**기술적 위험**
- **좌표 데이터 정합성**: `SelectedCoursePlaceResponse`(서버 응답)에는 위도/경도가 없다. 커스텀 코스 확정 시 `CourseCandidatePlace`는 사용자가 선택 화면에서 들고 있던 원본 장소 데이터(위경도 포함)로 구성해야 하며, 서버가 순서를 바꾸지 않는다는 전제(`sequence` 필드로 검증 필요)가 깨지면 장소-좌표 매칭이 틀어질 수 있다. → `sequence`로 매칭 검증 로직 필요.
- **호출부 3곳 동기화**: `film_roll_screen.dart`(컨트롤러 경유), `film_roll_progress_view.dart`(컨트롤러 경유), `film_roll_entry_flow.dart`의 `pushCourseSelectionAndConfirm`(유스케이스 직접 호출, 컨트롤러 미경유)이 서로 다른 패턴으로 `Navigator.push<CourseResponse>` 결과를 소비한다. 커스텀 코스 결과 타입을 추가하려면 이 세 곳 모두에서 "추천 코스 선택"과 "커스텀 코스 확정"을 분기 처리해야 한다. `Navigator.push` 제네릭 타입을 `CourseResponse`에서 sealed 타입(예: `CourseSelectionResult`)으로 바꾸는 변경이 필요할 가능성이 높다.
- **`BookmarkedPlace` 데이터 마이그레이션**: 필드를 추가하면 기존에 저장된 로컬 북마크 JSON에는 새 필드가 없다. `fromJson`에서 nullable 처리 또는 기본값 처리로 하위호환을 보장해야 하며, 필드가 없는 기존 북마크는 "코스 만들기" 진입 시 제외하거나 안내가 필요할 수 있다.
- **ACTIVE 코스 최대 3개 제약**: 서버가 강제하지만 UI에서도 선제적으로 막아야 함(이슈 요구사항). `addActiveCoursePlaces`와 `createCourse`의 책임 경계(이번 이슈는 생성만, 추가는 범위 밖)를 명확히 유지해야 다음 이슈와 충돌하지 않는다.
- **기존 ACTIVE 코스 대체**: `getActiveCourse` 조회 시점/실패 처리(계정 미로그인, 네트워크 오류 등)에 따라 "대체 확인" 다이얼로그를 못 띄우고 그냥 생성해버리는 경로가 없는지 확인 필요.

**비즈니스 위험**
- 장소 피커 UX가 복잡해지면(3종 소스 + 순서 지정 + 3개 제한) 사용자가 오히려 추천 코스보다 이탈할 가능성 → MVP 단계에서 최소 인터랙션(탭 순서로 자동 순번 부여 등)으로 단순화 검토 필요(구체적 UX는 `/analyze` 이후 `/design` 단계에서 결정).

## 7. 성공 기준

- [ ] 코스 선택 화면에서 추천/직접 만들기 모드를 전환할 수 있다.
- [ ] 관광지 목록, 검색, 북마크에서 장소를 골라 1~3개로 순서를 지정해 코스를 구성할 수 있다.
- [ ] 3개 초과 선택 시 UI에서 차단되고 안내된다.
- [ ] 확정 시 `CoursesApi.createCourse`가 호출되고, 성공 시 기존 코스 선택 완료와 동일하게 필름롤에 코스가 반영된다(로컬 DB 저장 포함).
- [ ] 이미 ACTIVE 코스가 있는 상태에서 새로 만들면 대체 확인 다이얼로그가 뜨고, 확인 후에만 생성이 진행된다.
- [ ] 북마크 화면/오버레이에서 "이 장소로 코스 만들기" 진입점을 통해 피커에 장소가 미리 담긴 채 진입한다.
- [ ] `CourseSelectionScreen`을 호출하는 3개 지점(`film_roll_screen.dart`, `film_roll_entry_flow.dart`, `film_roll_progress_view.dart`) 모두 회귀 없이 동작한다.
