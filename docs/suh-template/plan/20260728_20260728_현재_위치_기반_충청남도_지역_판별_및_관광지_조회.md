# 🎯 현재 위치 기반 충청남도 지역 판별 및 관광지 조회 전략 문서

## 1. 요약

`lib/features/location/` 에 이미 마련된 위치 권한 요청 로직(#30)을 실제 지역 판별·관광지 조회 흐름과 연동한다. 홈 화면 진입 시 위치 권한을 확인하고, 좌표를 획득해 Kakao Local API로 행정구역을 판별한 뒤, 충청남도인 경우에만 백엔드 `POST /api/regions/resolve`로 서비스 지역 여부를 최종 검증하고 반경 약 5km 이내 관광지 후보를 조회한다. 이번 범위는 **검증된 지역 정보 + 관광지 리스트를 상위 기능(지도/코스 추천/방문 인증)에 전달할 수 있는 지점까지**이며, 해당 하위 기능 자체의 UI 구현은 후속 작업으로 분리한다.

## 2. 배경 및 목적

**문제/필요성**:
- 위치 권한 요청 흐름(`lib/features/location/data/location_permission_service.dart`, `lib/features/location/presentation/location_permission_mockup_screen.dart`)은 마련되어 있으나 Mockup 단계이며, 획득한 좌표를 실제 행정구역 판별·관광지 조회로 연결하는 로직이 없다.
- `lib/data/models/resolve_region_request.dart`, `lib/data/models/region_response.dart` 모델이 정의만 되어 있고 실사용처(API 클래스)가 없다 — 직전 작업(#30) 전략 문서에서도 "별도 설계 필요"로 명시하고 이번 범위에서 제외한 바 있다.
- `lib/data/remote/places_api.dart`의 `getExternalPlaces`는 `regionId` 기준 조회만 지원하며, 좌표 기반 반경 조회는 없다.
- 좌표는 위경도 숫자값이지만 `ResolveRegionRequest`는 `provinceName`/`cityCountyName` 문자열을 요구하므로, 백엔드 호출 전에 FE에서 좌표 → 행정구역 문자열 변환(역지오코딩)이 반드시 필요하다.

**목표**:
- 홈 화면 진입 시 위치 권한 상태 확인 → (미허용 시) 권한 요청 → 좌표 획득 → 행정구역 판별 → 서비스 지역(충청남도) 검증 → 반경 5km 관광지 후보 조회까지 하나의 흐름으로 연결한다.
- 각 단계의 실패/예외 상황(권한 거부, 좌표 조회 실패, 서비스 지역 외, 관광지 조회 실패)에 대해 사용자에게 명확한 안내와 복구 경로(재시도/설정 이동/메인 복귀)를 제공한다.

**범위**:
- 포함: 좌표→행정구역 변환(Kakao Local API), `RegionsApi.resolveRegion` 연동, 반경 기반 관광지 조회 API 연동, Mockup 화면의 실제 화면 전환, 4종 예외 안내 화면, 홈 화면 진입 연동.
- 제외(후속 작업): 조회된 관광지를 실제로 표시하는 지도 화면, 코스 추천 로직, 방문 인증 기능 — 이번 작업은 이 기능들에 "검증된 지역 정보 + 관광지 리스트"를 전달할 수 있는 지점까지만 구현한다.

## 3. 요구사항

**필수 (P0)**
- Kakao Local API(좌표 → 행정구역 코드 변환, `coord2regioncode.json`) 연동을 위한 REST API 키를 `lib/core/config/app_secrets.dart`(및 `.example` 파일)에 추가
- 좌표 → 행정구역 문자열(시·도/시·군·구) 변환 서비스 추가 (`lib/features/location/data/`)
- `lib/data/remote/regions_api.dart` 신규 추가: `POST /api/regions/resolve` 호출, `ResolveRegionRequest` → `RegionResponse` (스펙 확정됨)
- `lib/data/remote/places_api.dart`에 반경 기반 관광지 조회 메서드 추가(기존 `getExternalPlaces` 확장 또는 신규 메서드)
- `location_permission_mockup_screen.dart`를 실제 위치 인증 화면으로 전환하고, 권한 확인 → 좌표 획득 → 행정구역 판별 → 지역 검증 → 관광지 조회 전체 플로우를 오케스트레이션
- 4종 예외 화면 구현: 권한 거부 안내, 위치 조회 실패 안내, 서비스 지역(충청남도) 외 안내, 관광지 데이터 조회 실패 안내
- 홈 화면(`lib/features/home/presentation/home_screen.dart`) 진입 시 위치 권한 상태 확인 및 위치 인증 화면 진입 연동

**중요 (P1)** — 우선순위: 안정성
- 각 외부 호출(Kakao Local API, `resolveRegion`, 관광지 조회)에 대해 명시적 타임아웃 설정 및 실패 시 원인이 구분되는 로깅(`dart:developer log`)
- 좌표 획득 실패, 지역 검증 실패, 관광지 조회 실패 각각에 수동 재시도 버튼 제공 (자동 재시도/백오프는 도입하지 않아 로직 단순성 유지)
- 한 세션 내 위치 인증에 성공한 경우, 홈 화면 재진입 시 불필요한 재검증(Kakao/백엔드 재호출)을 피하기 위한 인메모리 캐시 도입
- `permanentlyDenied` 상태에서 설정 이동 후 복귀 시 재검증 트리거 (기존 Mockup 화면의 `_onOpenSettingsTap` 흐름 계승)

**선택 (P2)**
- 관광지 조회 실패 화면에 실패 사유(네트워크/서버 오류)를 구분해 표시
- 디버그 모드에서 판별된 행정구역명·regionId·조회된 관광지 수를 화면에 노출 (QA 검증용)

## 4. 선택한 접근 방식

**방식**:
1. **좌표 → 행정구역 변환**: Kakao Local API의 좌표→행정구역 변환 API(`coord2regioncode.json`)를 신규 서비스(`lib/features/location/data/kakao_local_api_service.dart`, 가칭)에서 직접 호출한다. 이 API는 채록 백엔드(`AppSecrets.baseUrl`)가 아닌 카카오 외부 호스트(`dapi.kakao.com`)를 대상으로 하므로 `DioClient.instance`(백엔드 전용, `ApiResponse` 래퍼 가정)를 사용하지 않고 별도의 경량 `Dio` 인스턴스로 처리한다. 인증은 `Authorization: KakaoAK {REST API 키}` 헤더로 처리하며, 키는 로그인용 `kakaoNativeAppKey`와 별개로 `AppSecrets.kakaoRestApiKey`(신규)에 보관한다.
2. **지역 검증**: 변환된 시·도명이 "충청남도"가 아니면 백엔드 호출 없이 즉시 서비스 지역 외로 판단한다(불필요한 API 호출 절감). "충청남도"인 경우에만 `RegionsApi.resolveRegion(ResolveRegionRequest(provinceName, cityCountyName))`을 호출해 `RegionResponse(serviceArea, regionId, ...)`를 받는다. `serviceArea`가 false인 경우도 서비스 지역 외 화면으로 처리한다.
3. **관광지 조회**: `resolveRegion`으로 확보한 `regionId`와 현재 좌표(위도/경도), 반경(약 5km)을 파라미터로 `PlacesApi`의 신규 메서드를 호출해 관광지 후보를 조회한다. 이 엔드포인트의 정확한 경로/파라미터명은 백엔드와 최종 확인이 필요하며, 기존 `getExternalPlaces`(`GET /api/places/external`)와 동일한 컨벤션(쿼리 파라미터 + `PlaceListResponse` 재사용)을 따르는 것으로 가정해 설계한다.
4. **오케스트레이션**: 기존 `location_permission_mockup_screen.dart`와 동일하게 하나의 `StatefulWidget`이 내부 단계(enum 기반 상태)에 따라 콘텐츠를 분기하는 방식을 유지한다. 이 프로젝트는 별도 상태관리/유스케이스 계층 없이 화면이 서비스/API 클래스를 직접 호출하는 단순 구조(`HomeScreen`이 `UsersApi`를 직접 호출하는 것과 동일)이므로, 이번 기능도 같은 컨벤션을 따른다.
5. **홈 화면 연동**: `HomeScreen.initState`에서 위치 권한 상태를 확인하고, 권한이 없거나 이번 세션에 아직 위치 인증이 완료되지 않았다면 위치 인증 화면(신규)을 push한다. 뒤로가기/완료 시 `Navigator.pop`으로 홈으로 복귀하는 기존 패턴(`_onSettingsTap`과 동일)을 따른다.

**이유**: 프로젝트 전반이 Provider/Riverpod 등 상태관리 라이브러리 없이 `StatefulWidget`+`setState`와 static 서비스/API 클래스 조합만 사용하는 단순한 구조이므로, 새 추상화 계층(Repository, UseCase 등)을 도입하지 않고 기존 컨벤션을 그대로 확장하는 것이 일관성과 유지보수성 측면에서 유리하다. Kakao Local API는 이미 카카오 로그인 SDK를 사용 중이라 개발자 콘솔 연동 경험이 있고, 한국 행정구역 판별 정확도가 높아 채택했다.

**대안**:
- `geocoding` 패키지(OS 네이티브 지오코더): 별도 API 키가 불필요하나, 사용자가 API 키 관리 부담보다 네이티브 지오코더의 플랫폼별 결과 포맷 불일치·일부 기기 정확도 저하를 더 큰 리스크로 판단해 채택하지 않음(사용자 확인).
- 좌표를 그대로 백엔드에 전달해 백엔드가 변환+검증을 모두 수행: `ResolveRegionRequest`가 이미 문자열 기반으로 확정되어 있어 이번 범위에서 백엔드 계약을 변경하는 것은 협의 비용이 크다고 판단해 채택하지 않음(사용자 확인).
- 예외 상황별 별도 라우트(Screen) 4개를 독립적으로 만드는 방식: 홈 화면 진입 → 위치 인증 화면이라는 하나의 진입점 위에서 상태만 분기하는 편이 네비게이션 스택을 단순하게 유지하면서도 "뒤로가기 시 메인 복귀" 요구사항을 자연스럽게 만족시켜(위치 인증 화면 자체를 pop) 채택하지 않음.

| 좌표 → 행정구역 변환 | Kakao Local API (`coord2regioncode.json`) | 한국 주소 정확도, 기존 카카오 SDK 연동 경험 재사용 (사용자 확인) |
| Kakao Local API 호출 클라이언트 | `DioClient.instance` 미사용, 별도 경량 `Dio` 인스턴스 | `DioClient`는 채록 백엔드 전용(`ApiResponse` 래퍼, baseUrl 고정)이라 외부 호스트 호출에 부적합 |

| `resolveRegion` 연동 | `POST /api/regions/resolve`, `ResolveRegionRequest`→`RegionResponse` 그대로 사용 | 백엔드 스펙 확정 확인(사용자 제공: 요청/응답 모두 기존 모델과 완전히 일치) |
| 반경 기반 관광지 조회 엔드포인트 | 기존 `getExternalPlaces` 컨벤션을 따르는 신규 메서드로 설계, 실제 경로/파라미터는 구현 착수 전 백엔드 최종 확인 필요 | 사용자가 "기존 API 참고해서 같은 형식으로" 설계할 것을 요청했으나 정확한 경로·파라미터명이 아직 공유되지 않음 — 리스크로 별도 명시 |
| 충청남도 여부 1차 판별 | Kakao 변환 결과의 `provinceName`이 "충청남도"가 아니면 백엔드 호출 없이 즉시 서비스 지역 외 처리 | 불필요한 네트워크 호출 절감, 사용자 대기시간 단축 |
| 화면 구조 | Mockup 화면 1개를 실제 오케스트레이션 화면으로 전환, 예외 상황은 내부 상태 분기(별도 라우트 아님) | 기존 컨벤션(상태관리 라이브러리 없는 StatefulWidget 구조) 유지, 뒤로가기=메인 복귀 요구사항 자연 충족 |
| 이번 작업 범위 | 검증된 지역 정보 + 관광지 리스트 전달 지점까지 | 지도/코스 추천/방문 인증 UI는 후속 이슈로 분리 (사용자 확인) |
| 위치 인증 재검증 정책 | 세션 내 1회 성공 시 인메모리 캐시, 재진입 시 재호출 생략 | 안정성 우선(사용자 확인) — 불필요한 API 재호출로 인한 실패 가능성/지연 최소화 |

## 6. 고려사항 및 위험요소

**기술적 위험**:
- 반경 기반 관광지 조회 API의 정확한 스펙(경로, 파라미터명, 반경 단위)이 아직 문서로 확정되지 않음 — 대응: 구현 착수 전 백엔드와 최종 확인, 확인 전까지는 `PlacesApi` 확장 인터페이스만 설계하고 실제 연동은 스펙 확정 후 진행.
- Kakao Local API는 카카오 로그인과 별개로 REST API 키 발급·플랫폼(패키지명/번들 ID) 등록이 필요하며, 호출 도메인(`dapi.kakao.com`)이 앱의 네트워크 보안 정책(Android `usesCleartextTraffic`, iOS ATS)에 별도로 허용되어야 할 수 있음 — 대응: 빌드 후 실기기에서 호출 검증 필수.
- Kakao Local API·`resolveRegion`·관광지 조회 3개 외부 호출이 순차 의존 관계이므로 전체 대기시간이 누적될 수 있음 — 대응: 각 호출에 타임아웃을 명시하고, 로딩 상태를 단계별로 사용자에게 노출.
- 위치 서비스 자체가 꺼져있는 경우(OS 설정)와 권한은 있지만 좌표 조회가 실패하는 경우가 구분되지 않으면 사용자에게 잘못된 안내(재시도만 유도하고 실제 원인인 위치 서비스 OFF를 안내하지 못함)를 줄 수 있음 — 대응: `LocationPermissionService.isLocationServiceEnabled()`를 좌표 조회 실패 분기에서 함께 확인해 안내 문구를 분기.

**비즈니스 위험**:
- "관광지 후보"의 정확한 정의(개수 제한, 정렬 기준)가 이슈에 명시되어 있지 않음 — 대응: 백엔드 스펙 확인 시 함께 확정, 이번 계획에서는 API가 반환하는 리스트를 그대로 상위로 전달하는 것까지만 책임진다.
- 서비스 지역(충청남도) 외 사용자에 대한 "기능 제한" 범위가 구체적으로 정의되어 있지 않음(어떤 화면/버튼을 비활성화할지) — 대응: 이번 화면에서는 안내 문구와 메인 복귀 버튼까지만 구현하고, 실제 기능별 비활성화 처리는 각 기능(지도/코스추천/방문인증) 구현 시점에 해당 화면에서 처리하도록 범위를 명확히 분리.

## 7. 성공 기준

- [ ] `AppSecrets`에 Kakao REST API 키가 추가되고, 좌표 → 행정구역(시·도/시·군·구) 변환이 정상 동작함
- [ ] `RegionsApi.resolveRegion`이 `POST /api/regions/resolve`를 호출해 `RegionResponse`를 정상 파싱함
- [ ] 반경 기반 관광지 조회 메서드의 요청/응답 인터페이스가 설계되고, 백엔드 스펙 확인 후 실제 연동이 완료됨
- [ ] 홈 화면 진입 시 권한 미허용 상태면 위치 인증 화면으로 진입하고, 허용 상태면 좌표 획득부터 자동 진행됨
- [ ] 권한 거부/위치 조회 실패/서비스 지역 외/관광지 조회 실패 4가지 예외 상황이 각각 올바른 안내 화면과 복구 경로(재시도, 설정 이동, 메인 복귀)로 연결됨
- [ ] 세션 내 위치 인증 성공 후 홈 화면 재진입 시 불필요한 재검증 호출이 발생하지 않음
- [ ] 검증된 지역 정보(`RegionResponse`)와 관광지 리스트가 상위로 전달 가능한 형태로 반환되며, 지도/코스 추천/방문 인증 자체는 이번 범위에서 제외되었음을 문서에 명시
- [ ] 기존 `flutter analyze` 린트 규칙(`analysis_options.yaml`) 통과
