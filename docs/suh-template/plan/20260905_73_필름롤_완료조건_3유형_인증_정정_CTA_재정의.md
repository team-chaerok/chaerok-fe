# 🎯 이슈 #73 전략 문서 — 필름롤 완료 조건 "최소 3유형 인증" 정정 및 CTA 재정의

- 선행 의존: #72(지역 이탈 확정 → 현상 대기 → 현상 완료 라이프사이클, 완료됨)

## 1. 요약

필름롤의 완료(현상 가능) 판정이 로컬 "코스 전체 방문" 기준으로 잘못 구현되어 있어, 실제 서버 도메인 규칙("서로 다른 관광 유형 3종 이상 방문")과 어긋난다. `FilmRoll` 엔티티에 서버 `visitRequirementMet` 기반 판정을 흡수시키고, 기존 "필름롤 완료하기"(`FilmRollStatus.completed`로 전환하는 구 경로)를 폐기해 #72에서 이미 구현된 "지역 이탈 → 현상" 흐름(`ExitFilmRollUseCase`)으로 완전히 대체한다. 이 변경은 `film_roll_progress_view.dart`(채록길 탭)뿐 아니라, 동일한 완료 게이트를 쓰는 별도 화면 `film_roll_screen.dart`(코스선택→방문→완료 상세화면)에도 함께 적용한다.

## 2. 배경 및 목적

**문제/필요성**:

- `FilmRoll.isCompletable`(`lib/features/film_roll/domain/entity/film_roll.dart:61`)이 `selectedCourseId != null && visitedPlaceCount >= totalPlaceCount`로, 코스의 모든 장소를 방문해야만 활성화된다.
- 서버는 관광(TOURISM)/식당(FOOD)/카페·디저트(CAFE_DESSERT) 각 1곳 이상, 총 3개 서로 다른 유형 방문으로 현상 조건(`visitRequirementMet`, `VisitsApi.getVisits` 응답)을 판정하는데, 이 값이 클라이언트 완료 게이트에 전혀 반영되지 않는다.
- 조사 결과 문제가 이슈 본문이 언급한 것보다 넓다:
  - 동일한 `isCompletable` 게이트를 쓰는 화면이 **두 곳**이다 — `film_roll_progress_view.dart`(explore/채록길 탭, #72 이탈 흐름 완비)와 `film_roll_screen.dart`(홈/컬렉션에서 진입하는 상세화면, 이탈 흐름 없음).
  - `FilmRollRepositoryImpl.completeFilmRoll`(`lib/features/film_roll/data/repository/film_roll_repository_impl.dart:197-222`)이 엔티티의 `isCompletable`과 **별개로 자체 "전체 방문" 게이트를 중복 구현**하고 있어, 엔티티만 고쳐도 실제 완료 저장은 여전히 막힌다.
  - `VisitListResponse`(서버 응답)는 현재 `FilmRollProgressView`의 로컬 state에만 존재하고 `FilmRoll` 엔티티로 흘러들어가지 않는다.
- "필름롤 완료하기" 버튼이 가리키는 실제 도메인 개념("지역 이탈 확정 → 현상 시작")과 문구·동작이 어긋난다.

**목표**:

- 완료(현상 가능) 판정을 서버 `visitRequirementMet` 기준(로컬 폴백 포함)으로 통일한다.
- "필름롤 완료하기" 개념을 완전히 폐기하고 "지역을 벗어나 현상하기"(#72 이탈 흐름)로 대체해, `completed`/`developing`/`expired` 두 갈래 상태 체계를 하나로 정리한다.
- 두 화면(explore 탭, 상세화면) 모두에서 일관된 동작을 보장한다.

**범위**:

- 포함: `FilmRoll` 엔티티 확장, `isCompletable` 판정 로직 교체, `film_roll_progress_view.dart` + `film_roll_screen.dart` CTA 재정의, `completeFilmRoll`/`CompleteFilmRollUseCase`/`FilmRollStatus.completed` 관련 코드 제거·대체, `film_roll_collection_screen.dart`의 `completed` 상태 표시 분기 정리, 진행률 표시("유형 N/3") 조정, 관련 단위 테스트 수정.
- 제외: 현상 완료(READY_TO_RENDER 이후 실제 필름 현상 처리) 자체 — #72에서 "이번 범위 밖(후속 이슈)"로 명시됨. 서버 API 스펙 변경 없음(기존 `VisitsApi.getVisits` 응답 필드만 사용).

## 3. 요구사항

**필수 (P0)**:

- `FilmRoll` 엔티티에 `visitRequirementMet`(서버 판정), `visitedCategoryCount`, `requiredCategoryCount`(nullable) 필드 추가. `isCompletable`을 이 값 우선 사용, 값이 없으면(서버 미동기화) 로컬 폴백(서로 다른 유형 카운트 ≥ 3)으로 대체.
- `film_roll_progress_view.dart` + `film_roll_screen.dart`의 "필름롤 완료하기" CTA를 "지역을 벗어나 현상하기"로 교체하고, 두 화면 모두 `ExitFilmRollUseCase`(기존 `_startExit()`/`FilmRollModule.instance.exitFilmRoll` 재사용) 흐름에 연결.
- `completeFilmRoll`(Repository/UseCase/`FilmRollController.completeFilmRoll`/`FilmRollStatus.completed` 전환 로직) 제거 또는 이탈 흐름으로 리다이렉트. `FilmRollNotCompletableException` 등 관련 예외 정리.
- 3유형 미충족 상태에서 이탈 시도 시 "지금 벗어나면 현상되지 않아요" 경고 다이얼로그 추가(현재 `_showExitConfirmDialog()`는 무조건 이탈 확인만 함 — 유형 미충족 분기 신설 필요).
- 진행률 표시를 "방문 N/전체 장소"에서 "서로 다른 유형 N/3" 중심으로 조정(두 화면 모두). `film_roll_progress_view.dart`는 이미 `_developConditionLabel()`로 유사 라벨을 별도 렌더링 중 — 이를 엔티티 값 기반으로 통합.

**중요 (P1)**:

- `film_roll_collection_screen.dart`의 `FilmRollStatus.completed` 분기(라벨 "완료 · N곳 방문", 아이콘) 정리 — `completed` 상태가 더 이상 발생하지 않으면 `developing`/`expired` 중심으로 재작성하거나, 기존 데이터 호환을 위해 표시만 유지할지 결정.
- `FilmRoll.progress`(0.0~1.0, 전체 방문 기준) getter의 존속 여부 검토 — UI에서 "유형 N/3"로 대체되면 `progress`는 더 이상 CTA/게이트에 쓰이지 않으나, 참고용 진행 바 표시에는 남을 수 있음.

**선택 (P2)**:

- 유형별(TOURISM/FOOD/CAFE_DESSERT) 개별 체크리스트 UI(현재 `VisitListResponse`에 유형별 개별 카운트 필드는 없고 `visits: List<VisitItemResponse>`만 있음 — 필요 시 클라이언트에서 그룹핑). 이슈 본문에 명시되지 않은 확장이므로 이번 스코프에서는 보류.

## 4. 선택한 접근 방식

**방식**: `FilmRoll` 엔티티에 서버 방문 요건 데이터를 흡수시키고, 구 완료 경로(`completeFilmRoll`)를 폐기해 이탈 흐름(`exitFilmRoll`) 단일 경로로 통합. 두 화면(explore 탭, 상세화면) 모두 수정.

**이유**:

- 엔티티 확장 시 `isCompletable`이 단일 진실 공급원(single source of truth)이 되어, 두 화면이 동일 getter를 재사용하면 동작 일관성이 자연히 보장된다. 화면별로 헬퍼 함수를 따로 두면 로직이 중복되고 두 화면이 다시 어긋날 위험이 있다(현재도 이미 이 문제로 CTA 활성화 조건과 라벨 표시 조건이 따로 놀고 있음).
- 구 경로를 남겨두면 `completed`/`developing`/`expired` 상태가 서로 다른 게이트로 계속 병존해, "완료"의 의미가 두 갈래로 갈라진 채 유지보수 부담이 커진다. 이슈 취지 자체가 "완료 개념을 이탈→현상 흐름으로 재정의"이므로 완전 대체가 근본적 해결이다.
- `film_roll_screen.dart`를 방치하면 같은 앱 안에서 진입 경로(홈/컬렉션 vs 채록길 탭)에 따라 완료 조건과 CTA 동작이 달라지는 불일치가 남는다.

**대안**:

- (기각) `film_roll_progress_view.dart`만 수정: 이슈 본문 파일 목록과 일치하지만, `film_roll_screen.dart`가 실사용 진입점(홈 대시보드·컬렉션 화면에서 직접 연결)으로 남아 있어 사용자가 두 화면에서 다른 동작을 겪게 됨. 사용자 확인 결과 두 화면 모두 수정으로 결정.
- (기각) `completeFilmRoll` 게이트 조건만 3유형 기준으로 수정하고 경로는 유지: 작업량은 적지만 `completed`와 `developing`/`expired`가 별도 상태로 계속 분기되어, "완료 = 현상 시작"이라는 이슈의 핵심 재정의가 이름만 바뀐 채 구조적으로는 미완성 상태로 남음. 사용자 확인 결과 완전 대체로 결정.

## 6. 고려사항 및 위험요소

**기술적 위험**:

- `completeFilmRoll` 제거 시 기존 로컬 DB에 이미 `FilmRollStatus.completed`로 저장된 레코드가 있다면(과거 사용자 데이터) 컬렉션 화면 표시가 깨질 수 있음 → `FilmRollStatus.completed` enum 값 자체는 유지하고, 신규 전환 경로만 제거하는 방식으로 대응.
- `film_roll_screen.dart`에는 현재 지역 이탈 감지 로직(`_checkRegionDeparture`, 카카오 역지오코딩)이 없음 → CTA를 이탈 흐름에 연결하려면 이 화면에서도 이탈 확인 다이얼로그를 띄우는 진입점(버튼 탭 시 확인 다이얼로그, 자동 감지는 불필요할 수 있음)을 별도로 설계해야 함. 자동 위치 감지까지 이식할지는 구현 단계(`/analyze`)에서 두 화면의 실제 사용 빈도·UX 요구를 보고 판단.
- `VisitListResponse`를 엔티티에 흡수시키는 시점(코스 선택 화면 로드 시 `getVisits` 호출 필요) — 현재 `FilmRoll` 로드 경로(`FilmRollController`/`FilmRollRepository`)에 `VisitsApi` 호출이 없으므로 어디서 언제 호출해 엔티티를 갱신할지 설계 필요.

**비즈니스 위험**:

- 완료 개념 변경으로 "완료했어요!" 메시지 등 사용자 대면 문구가 여러 곳(스낵바 메시지 등)에서 바뀌어야 함 — 문구 일관성 누락 위험. `_onCompleteTap`류 콜백 내 하드코딩된 성공 메시지를 전수 확인 필요.

## 7. 성공 기준

- [ ] `FilmRoll.isCompletable`이 서버 `visitRequirementMet` 우선, 미동기화 시 로컬 유형 카운트(≥3) 폴백으로 판정된다.
- [ ] `film_roll_progress_view.dart`, `film_roll_screen.dart` 두 화면 모두 "지역을 벗어나 현상하기" CTA로 문구·동작이 통일되고, 탭 시 `ExitFilmRollUseCase` 흐름으로 연결된다.
- [ ] 3유형 미충족 상태에서 이탈 시도 시 경고 다이얼로그가 노출된다.
- [ ] `completeFilmRoll`/`CompleteFilmRollUseCase` 관련 신규 진입 경로가 제거되고, 기존 테스트(`film_roll_repository_impl_test.dart`의 completeFilmRoll 관련 케이스)가 새 흐름에 맞게 갱신된다.
- [ ] 진행률 표시가 "서로 다른 유형 N/3" 중심으로 두 화면에서 동일하게 보인다.
- [ ] 관련 단위 테스트(엔티티 `isCompletable`, exit 흐름, repository)가 모두 통과한다.
