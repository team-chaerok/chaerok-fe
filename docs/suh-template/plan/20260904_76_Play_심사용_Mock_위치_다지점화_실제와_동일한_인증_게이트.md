# 🎯 Play 심사용 Mock 위치 다지점화 + 실제와 동일한 인증 게이트 — 전략 문서

- 이슈: [#76](https://github.com/team-chaerok/chaerok-fe/issues/76) `🚀[기능개선][테스트]`
- 작성일: 2026-09-04
- 단계: Plan (전략 수립) — 코드 수정 없음. 다음 단계는 `/analyze`.

---

## 1. 요약

Play 심사(테스트 계정)에서 **실제 이동 없이** 방문 인증 흐름 전체를 재현할 수 있어야 한다.
현재 `MockLocationProvider`는 지역당 좌표 1개·`accuracy: 0`만 반환해 (1) 코스의 여러 스팟을
각각 인증할 수 없고 (2) 정확도 게이트(`kVisitMinGpsAccuracyMeters` = 50m)를 사실상 우회하며
(3) 애초에 방문/진행 흐름이 `LocationProviderFactory`가 아니라 `LocationPermissionService`를
직접 호출해 Mock이 게이트까지 도달하지도 않는다. 또한 Play 심사 빌드는 통상 release라
`LocationProviderFactory`의 `kReleaseMode` 가드에 막힌다.

해결책은 **방문 성공을 강제 반환하지 않고 좌표만 바꿔** 실제 `evaluateVisitGate`를 그대로
통과시키는 것이다. 구체적으로 ① Mock 좌표를 지역당 다지점(4개 지역 모두 ≥ 3개)으로 확장하고
현실적인 `accuracy`(< 50m)를 반환, ② QA 화면에 "현재 Mock 지점" 선택 UI + `AppPreferences`
저장 추가, ③ Mock 좌표가 방문 게이트까지 흐르도록 위치 조회 경로를 정리, ④ release에서도
**서버가 내려주는 테스트 계정 플래그(`user.isTester` 류)** 를 가진 계정에 한해 Mock을
허용하는 게이트를 신설한다. release 일반 사용자 차단은 그대로 유지한다.

## 2. 배경 및 목적

### 문제 / 필요성

| # | 현상 | 근거 |
|---|------|------|
| P-1 | 코스의 여러 스팟(각 100m 이내)을 인증 불가 | `MockLocationProvider._regionCoordinates`가 지역당 좌표 1개 (`lib/core/location/mock_location_provider.dart:7-12`) |
| P-2 | 정확도 게이트를 우회 | Mock이 `accuracy: 0` 반환 → `evaluateVisitGate`의 `position.accuracy > 50` 검사를 항상 통과 (`visit_verification.dart`) |
| P-3 | 어느 스팟에 있는지 고를 수단 없음 | QA UI(`my_screen.dart _buildMockLocationDebugCard`)에 지역 선택만 있고 지점 선택 없음 |
| P-4 | Mock 좌표가 방문 게이트에 도달조차 안 함 | `explore_screen._loadCurrentPosition()`이 `LocationPermissionService.getCurrentPosition()`을 직접 호출 → `MockLocationProvider` 우회 (`lib/features/explore/presentation/explore_screen.dart:107`) |
| P-5 | Play 심사(release) 빌드에서 Mock 원천 차단 | `LocationProviderFactory.create()`의 `if (kReleaseMode) return RealLocationProvider()` + QA 카드가 `kDebugMode` 전용 |

### 목표

- 테스트 계정이 **실제 게이트(`evaluateVisitGate`)를 실제와 동일한 조건**(50m accuracy, 100m 거리)으로
  통과하며 코스의 여러 스팟을 순차 인증할 수 있다.
- 방문 성공 강제 분기(테스트 계정이면 무조건 성공) **를 두지 않는다.**
- release 일반 사용자의 Mock 차단은 **현행 유지**.

### 범위

**포함**
- `MockLocationProvider` 다지점 지원 + 선택 지점 좌표/현실적 `accuracy` 반환
- 4개 지역(공주·부여·서산·예산) 모두 테스트 좌표 세트 ≥ 3개 (하드코딩 상수)
- QA/디버그 화면에 "현재 Mock 지점" 선택 UI + `AppPreferences` 저장
- Mock 좌표가 방문 게이트까지 흐르도록 위치 조회 경로 정리
- 서버 `user.isTester` 류 플래그 기반 테스트 계정 Mock 게이트
- 좌표 세트가 추천 코스 스팟과 어긋나지 않는지 **수동 확인 절차** 문서화

**제외**
- 방문 성공 강제 반환 / 게이트 우회 로직
- `evaluateVisitGate` 자체 로직 변경 (이미 `main`에 존재 — #69)
- 방문 인증 시점 좌표 실시간 재조회 (별도 이슈 [#77])
- 백엔드의 `isTester` 필드 구현 자체 (FE는 소비만; BE 협의 필요)
- 좌표 세트 ↔ 코스 스팟 자동 교차검증 테스트 (이번 범위는 수동 확인)

## 4. 선택한 접근 방식

### 4-1. 좌표 세트 관리 — **A. 하드코딩 상수 세트 + 수동 확인 절차**

`MockLocationProvider`와 같은 레이어에 지역별 `const` 좌표 세트를 둔다. 각 항목은
`(라벨, 위도, 경도)` 형태이며 값은 해당 지역 추천 코스의 실제 스팟에서 손으로 골라 100m 이내로 잡는다.

```
// 예시 형태 (구현 아님 — /analyze·/implement 단계에서 확정)
const _regionMockSpots = {
  RegionCode.gongju: [
    (label: '공산성', latitude: 36.xxxx, longitude: 127.xxxx),
    (label: '무령왕릉', latitude: 36.xxxx, longitude: 127.xxxx),
    (label: '국립공주박물관', latitude: 36.xxxx, longitude: 127.xxxx),
    (label: '제민천', latitude: 36.xxxx, longitude: 127.xxxx),
  ],
  RegionCode.buyeo: [ ... ≥ 3 ],
  RegionCode.seosan: [ ... ≥ 3 ],
  RegionCode.yesan: [ ... ≥ 3 ],
};
```

- **이유**: 예측 가능하고 오프라인에서 동작하며, Play 심사처럼 "정해진 시나리오를 그대로 밟는"
  용도에 맞는다. 코스 API 로딩 순서에 의존하지 않아 지역 진입·코스 선택 이전 흐름에서도 쓸 수 있다.
- **대안 B (로드된 코스에서 동적 파생)**: 항상 실제 스팟과 일치하지만, 코스가 로드되기 전에는
  지점을 고를 수 없고(닭-달걀), 코스 데이터가 없는 흐름을 못 덮는다. → 미채택.
- **드리프트 대응**: 백엔드 코스/스팟 좌표가 바뀌면 상수가 어긋날 수 있으므로 **수동 확인 절차**
  (§6, §7)를 문서로 남긴다. 자동 검증 테스트는 P2/후속.

### 4-2. Mock → 게이트 도달 경로 — **분석 단계에서 확정 (후보 2개)**

현재 방문/진행 흐름은 `LocationPermissionService.getCurrentPosition()`을 직접 부른다.
Mock을 게이트까지 흐르게 하는 방법 2가지를 `/analyze`에서 코드 기준으로 확정한다.

| 후보 | 방법 | 장점 | 단점 |
|------|------|------|------|
| **C-1** `LocationPermissionService`를 mock-aware로 | `getCurrentPosition()` 내부에서 "Mock 허용 && Mock ON"이면 `MockLocationProvider` 좌표 반환 | 호출부 변경 없음, 모든 흐름(촬영·진행·위치인증)에 일괄 적용 | 권한 서비스에 팩토리/설정 의존이 생겨 레이어 경계가 흐려짐 |
| **C-2** 흐름을 `LocationProviderFactory` 경유로 전환 | `explore_screen` 등이 `LocationProviderFactory.create()` 사용하도록 리팩터 | 추상화가 깔끔, 팩토리가 유일한 분기점 | 변경 범위 큼, `LocationVerificationScreen`은 이미 팩토리를 쓰므로 흐름별 경로가 이원화 |

> 권고: **C-1을 기본선**으로 검토하되(#77 "탭 시점 재조회"와도 자연스럽게 합쳐짐),
> `/analyze`에서 `LocationVerificationScreen`의 팩토리 사용 패턴과 충돌 여부를 확인 후 최종 결정.

### 4-3. Play 심사 도달 — **테스트 계정 게이트 신설 (서버 플래그 기반)**

`LocationProviderFactory.create()`의 게이트를 다음과 같이 재정의한다 (의사 결정만; 구현은 후속):

```
release 빌드:
  - user.isTester == true         → Mock 설정 존중 (ON이면 MockLocationProvider)
  - 그 외 / 비로그인 / 필드 없음   → 항상 RealLocationProvider   (현행 유지)
debug/profile 빌드:
  - 현행대로 Mock 설정 존중
```

- **식별자**: `/api/users/me` 응답의 `isTester`(불리언) 같은 플래그. 현재 `UserResponse`에는
  `role`(user/admin)만 있으므로 **백엔드에 필드 추가 협의가 선행**돼야 한다.
- **FE 파싱 원칙**: 필드 부재/파싱 실패 시 `false`. 캐시된 사용자 정보로 판단하고, 없으면 Real.
- **대안 / 인터림**: BE 일정이 늦으면 임시로 `role == UserRole.admin`을 테스트 계정으로 간주
  (P2). 프론트 하드코딩 이메일 허용목록은 유지보수·유출 리스크로 비채택.
- **강제 성공 분기 없음**: 이 게이트는 "Mock 좌표를 쓸 수 있는가"만 결정하며, 방문 인증 자체는
  `evaluateVisitGate`가 그대로 판정한다.

### 4-4. QA 지점 선택 UI

- 위치: 기존 Mock 카드가 있는 **`my_screen.dart _buildMockLocationDebugCard`** 에 지점 선택
  드롭다운을 추가 (이슈가 가리킨 `settings_screen.dart`에는 Mock UI가 없음 — 참조 오류로 판단).
- release + 테스트 계정에서도 이 카드가 보이도록 노출 조건을 `kDebugMode` → `kDebugMode || isTester`로 확장.
- 저장: `AppPreferences`에 `mock_spot_index`(또는 라벨) 키 추가. 지역 변경 시 인덱스 범위 밖이면 0으로 클램프.

### 4-5. 베이스 브랜치 정리 (선결)

현재 작업 브랜치 `20260904_#76_...`는 #66 시점(`3084e02`)에서 분기돼 **#69의 `visit_verification.dart`가
없다.** #69는 이미 `origin/main`(`262e4e9`)에 머지됨. → **이 브랜치를 `main`에 리베이스**한 뒤 작업 시작.

## 5. 주요 결정사항

| 결정 | 선택 | 이유 |
|------|------|------|
| 좌표 세트 소스 | 하드코딩 `const` 세트 + 수동 확인 절차 | 예측 가능·오프라인·로딩 순서 무관. Play 심사 시나리오에 적합 |

| Mock→게이트 경로 | `/analyze`에서 C-1(기본) vs C-2 확정 | 코드 레이어 영향 범위를 실측 후 결정 |
| Play 심사 도달 | 서버 `isTester` 플래그 게이트 신설 | release 일반 사용자 차단 유지하며 테스트 계정만 허용 |
| 테스트 계정 인터림 | `role == admin` 허용 (P2, BE 지연 시) | 필드 추가 전에도 QA 가능 |
| 강제 성공 분기 | 두지 않음 | 이슈 핵심 요구 — 실제 게이트와 동일 검증 |
| release 가드 | 일반 사용자 대상 현행 유지 | 이슈 명시 |
| QA UI 위치 | `my_screen.dart` Mock 카드 | 기존 Mock 토글이 여기 있음 (이슈의 settings_screen 참조는 오류) |
| 브랜치 베이스 | `main`에 리베이스 후 시작 | #69의 게이트 도메인 모델 필요 |

## 7. 좌표 세트 ↔ 코스 스팟 수동 확인 절차 (초안)

1. 대상 지역의 추천 코스를 앱/`PlacesApi.getExternalPlaces(regionId)`로 조회해 스팟 좌표 목록 확보.
2. 각 Mock 후보 좌표에 대해 가장 가까운 코스 스팟과의 거리를 `Geolocator.distanceBetween`으로 계산.
3. **거리 ≤ 60m** 면 채택(게이트 100m에 여유), 60~100m면 좌표 재조정, 100m 초과면 폐기.
4. 채택 좌표에 `(label, 기준 스팟명, 실측 거리, 확인일)` 주석을 상수 파일에 남긴다.
5. 코스 데이터가 개편될 때 이 절차를 재수행하는 규칙을 `docs/`(또는 상수 파일 주석)에 명시.
