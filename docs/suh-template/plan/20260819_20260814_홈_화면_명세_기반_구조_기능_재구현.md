## 🎯 홈 화면 명세 기반 구조/기능 재구현 전략 문서

> 관련 이슈: [#55](https://github.com/team-chaerok/chaerok-fe/issues/55)
> 다음 단계: `/analyze` → `/implement`

### 1. 요약

현재 홈 화면(`HomeDashboardScreen`)은 5탭 재구성 작업 이후 헤더와 진행 중 필름롤 카드만 노출하는 축소된 상태다. 목표 명세 대비 빠진 3개 섹션(날씨 카드, 필름롤 촬영 진행률+사진 캐러셀, 가까운 채록 장소 리스트)을 하드코딩/mock 없이 실제 API·repository 연동으로 복원한다. 디자인(색상, 레이아웃 세부 수치)은 범위 제외이며 데이터·컴포넌트 구조만 다룬다.

### 2. 배경 및 목적

**문제/필요성**: 5탭 재구성(`20260802_...5탭_도입.md`) 이후 홈 화면 정보 구조가 목표 명세보다 임의로 축소됨. 사용자가 홈에서 오늘의 기록 맥락(날씨/필름롤 현황/주변 채록 가능 장소)을 파악할 수 없음.

**목표**: 3개 섹션을 실데이터로 홈 화면에 복원. 날씨 데이터 소스 확정, 필름롤 사진 캐러셀 데이터 경로 신설, 채록길 탭과 중복 없는 "가까운 채록 장소" 리스트 구현.

**범위**:
- 포함: 날씨 카드(지역명+날씨상태/기온), 필름롤 진행률+촬영 사진 가로 캐러셀, 가까운 채록 장소 리스트(사진/이름/카테고리/거리/채록 여부), 관련 provider/repository 연동.
- 제외: 디자인 세부 수치(색상/레이아웃), `lib/ui/home` 프리뷰 자산 복원(이미 삭제됨, 참고 자산 없음), 백엔드 신규 엔드포인트 구현(프론트는 외부 API 직접 호출).

### 3. 요구사항

**필수 (P0)**
- 날씨 카드: 기상청 공공데이터 단기예보 API 연동, 지역명 + 날씨상태/기온 표시.
- 필름롤 캐러셀: `ActiveFilmRollCard`를 진행률 + 촬영된 사진 가로 스크롤로 확장(계획 문서 P1 항목 승격).
- 가까운 채록 장소: `LocationVerificationResult.places`(세션 캐시) 재사용, 각 카드에 채록(방문) 완료 여부 표시.
- 3개 섹션 모두 실제 API/repository 연동, mock 데이터 금지.

**중요 (P1)**
- 위치 인증 미완료 상태에서의 로딩/빈 상태 UX(날씨 카드, 채록 장소 리스트 모두 위치 좌표에 의존).
- 필름롤이 없는 상태(신규 사용자)에서 캐러셀 섹션 처리(현재 `_buildStartFilmRollCard()`와의 공존).

**선택 (P2)**
- 날씨 상태 아이콘 매핑(기상청 코드 → 아이콘)은 디자인 자산이 확정되면 후속 작업.

### 4. 선택한 접근 방식

**방식**: 기존 `HomeDashboardScreen` 상태 관리 패턴(개별 `Future<void> _fetchX()` + `setState`)을 그대로 유지하며, 각 섹션을 독립 위젯 + 독립 데이터 소스로 추가하는 점진적 확장. 신규 외부 API(기상청)는 `KakaoLocalApiService`와 동일한 패턴(전용 `Dio` 인스턴스 + `AppSecrets`)으로 별도 서비스 클래스로 분리.

**이유**:
- `HomeDashboardScreen`은 이미 여러 개의 독립적인 `_fetchX()`/`setState` 흐름(유저 정보, 위치 인증, 필름롤 복구)이 공존하는 구조라 새 섹션도 동일 패턴으로 자연스럽게 확장 가능(코드 스타일 일관성).
- 기상청 API는 채록 백엔드(`DioClient`)와 무관한 외부 호스트이므로, Kakao Local API와 동일하게 별도 서비스로 분리하는 것이 기존 컨벤션과 일치.
- "가까운 채록 장소"는 `LocationVerificationResult.places`를 재사용해 `explore_screen.dart`의 `PlacesApi.getExternalPlaces` 별도 호출을 피함(중복 API 호출 및 로직 제거).

**대안**:
- Provider/Riverpod 등 상태관리 라이브러리 도입 → 기각. 프로젝트 전반에 그런 패턴이 없고(기존 `StatefulWidget` + 로컬 상태가 표준), 이번 작업 범위를 벗어나는 아키텍처 변경이 됨.
- "가까운 채록 장소"에서 `explore_screen`처럼 자체 `PlacesApi` 재호출 → 기각. 위치 인증 흐름에서 이미 조회된 데이터를 세션 캐시로 갖고 있어 중복 호출이 불필요(사용자 확인 완료).

### 5. 주요 결정사항

| 결정 | 선택 | 이유 |
|------|------|------|
| 날씨 데이터 소스 | 기상청 공공데이터 단기예보 API | 무료, 서비스 지역(충남 4개 시군)에 특화, 사용자 확정 |
| 가까운 채록 장소 데이터 소스 | `LocationVerificationResult.places` 세션 캐시 재사용 | `explore_screen.dart`와 중복 API 호출 방지, 사용자 확정 |
| 작업 진행 단위 | 3개 섹션 한 번에 계획 (구현 단계에서 커밋 단위 분리 가능) | 이슈 하나가 3개 섹션을 모두 요구, 사용자 확정 |
| 날씨 API 연동 위치 | 신규 `WeatherApiService` — `KakaoLocalApiService`와 동일 패턴(별도 Dio, `AppSecrets`) | 기존 외부 API 연동 컨벤션과 일치 |
| 필름롤 사진 조회 경로 | `PhotoRepository`에 필름롤 단위 조회 메서드 신설 필요 (현재 `findByPlace(placeId)`만 존재) | 캐러셀은 필름롤 전체 사진이 필요하나 기존 API는 장소 단위만 지원 |
| 채록 여부 판정 | 후보 장소의 `id`/`kakaoPlaceId`/`tourContentId`를 `FilmRollPlace.serverPlaceId`/`externalPlaceId`와 매칭 | 기존 엔티티 필드로 커버 가능, 신규 필드 불필요 |

### 6. 고려사항 및 위험요소

**기술적 위험**:
- 기상청 API는 위경도가 아닌 격자 좌표(nx/ny)를 요구 — 좌표 변환 로직(공식 변환식) 신규 구현 필요. 대응: `WeatherApiService` 내부에 변환 유틸을 캡슐화하고 단위 테스트로 검증.
- 기상청 API는 발표 시각 기준 최신 단기예보만 제공(호출 시각에 따라 조회 가능한 `base_date`/`base_time` 계산 필요). 대응: 관측/발표 주기 규칙을 상수화해 별도 헬퍼로 분리.
- `PhotoRepository`/`PhotoLocalDataSource`에 필름롤 단위 사진 조회 메서드가 없어 신규 쿼리 추가 필요(로컬 DB, Drift 추정) — 스키마 변경은 없고 쿼리만 추가되므로 마이그레이션 리스크는 낮음.
- 위치 인증이 완료되지 않은 상태(`_locationResult == null`)에서 날씨 카드/채록 장소 섹션이 데이터 없이 렌더링됨 — 기존 헤더의 "확인 중..." 패턴과 동일한 로딩 표시로 일관성 유지.

**비즈니스 위험**:
- 이슈 상 백엔드/프론트 담당자가 모두 "미정" — 이번 작업은 프론트 단독으로 외부 API(기상청) 직접 연동을 전제로 함. 추후 백엔드가 날씨 프록시를 제공하기로 결정되면 `WeatherApiService` 내부 구현만 교체(인터페이스 유지)하면 되도록 설계.
- 기상청 공공데이터 API 키 발급 필요(공공데이터포털 신청) — 실 연동 전 API 키 확보가 선행 조건.

### 7. 성공 기준

- [ ] 홈 화면에 날씨 카드(지역명 + 날씨상태/기온)가 실제 기상청 API 데이터로 표시된다.
- [ ] 진행 중 필름롤이 있을 때 `ActiveFilmRollCard`가 촬영 진행률 + 촬영된 사진 가로 캐러셀을 실데이터로 표시한다.
- [ ] "가까운 채록 장소" 리스트가 세션 캐시된 위치 인증 결과를 사용해 사진/이름/카테고리/거리/채록 여부를 표시한다.
- [ ] 위치 인증 미완료/필름롤 없음 등 빈 상태에서도 크래시 없이 로딩/대체 UI가 노출된다.
- [ ] 3개 섹션 모두 mock 데이터 없이 실제 API/repository 응답으로 동작한다.
