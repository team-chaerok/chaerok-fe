## 🎯 계정 전환 시 이전 계정 로컬 필름롤 데이터 노출 방지 전략 문서

> 대상 이슈: `#45` (브랜치 `20260730_#45_계정_전환_시_이전_계정_로컬_필름_롤_데이터_노출`)
> ⚠️ `get-issue-number` CLI가 브랜치명의 날짜(`20260730`)를 이슈번호로 오인식하는 버그를 확인했다(실제 이슈번호는 `45`). 이 문서의 파일명은 브랜치명을 근거로 수동 교정한 값을 사용한다.

### 1. 요약

카카오 계정 로그아웃 후 구글 계정으로 로그인하면, 카카오 계정 사용 중 로컬 Drift DB에 쌓인 필름롤(및 연관 장소/사진) 데이터가 그대로 새 계정 세션에 노출된다. 근본 원인은 (a) 로그아웃이 로컬 DB를 전혀 정리하지 않고, (b) 로컬 스키마 자체에 계정 구분 컬럼이 없어 `findAll()` 등 모든 조회가 계정 구분 없이 테이블 전체를 반환하기 때문이다. 이번 전략은 `film_rolls` 테이블에 계정 식별자(`userId`) 컬럼을 추가하고 모든 로컬 조회/생성 경로를 현재 로그인 계정 기준으로 스코핑하는 방식으로 근본 해결한다.

### 2. 배경 및 목적

**문제/필요성**
- `lib/features/settings/presentation/settings_screen.dart:33-53`의 `_onLogoutTap`은 `AuthApi.logout` 호출 후 `TokenStorage.instance.clear()`로 보안 저장소의 액세스/리프레시 토큰만 삭제한다. `AppDatabase`/`FilmRollModule`에 대한 정리 호출이 전혀 없다.
- `lib/core/database/local_database.dart:24,54-59`는 앱 전체가 공유하는 단일 `AppDatabase` 싱글턴이며, 고정 파일 `chaerok_local.sqlite` 하나만 사용한다.
- `film_rolls_table.dart` / `film_roll_places_table.dart` / `photos_table.dart`에는 `userId`/`accountId` 성격의 컬럼이 전혀 없다.
- `lib/features/film_roll/data/local/film_roll_local_data_source.dart:27-31`의 `findAll()`은 `WHERE` 절 없이 테이블의 모든 행을 반환하며, `findById`/`findActiveByRegion`/`watchById` 역시 계정 구분 없이 id/지역코드만으로 조회한다.
- `lib/features/auth/presentation/login_screen.dart:89-122`의 `_handleLoginResponse`는 로그인 성공 시 토큰만 저장할 뿐, 로그인한 계정의 식별자를 로컬에 기록하거나 이전 세션과 비교하는 로직이 없다.
- 서버 응답(`OAuthLoginResponse`/`TokenResponse`, `lib/data/models/o_auth_login_response.dart`, `token_response.dart`)에는 계정 식별자가 포함되지 않는다. 계정 id는 별도로 `UsersApi.getMyInformation()` (`lib/data/remote/users_api.dart:11-17`, `/api/users/me`)을 호출해야 얻을 수 있으며, 현재는 `home_dashboard_screen.dart`/`my_screen.dart`/`profile_edit_screen.dart`에서 화면 표시 용도로만 쓰이고 인증 흐름과는 연결되어 있지 않다.

**목표**
- 로그아웃 후 다른 계정으로 로그인해도 이전 계정이 만든 필름롤/방문 장소/사진이 새 계정 세션에 보이지 않도록 한다.
- 앱 프로세스를 재시작하지 않고 로그아웃→다른 계정 로그인을 연속으로 수행해도(같은 프로세스 내 싱글턴 재사용 케이스) 동일하게 격리되어야 한다.

**범위**
- 포함: `film_rolls` 테이블 계정 스코프 도입, 관련 조회/생성 경로 필터링, 로그인/로그아웃 시 계정 식별자 로컬 관리, 이 구조를 사용하는 `FilmRollModule`/데이터소스 경로 정리.
- 제외(이번 스코프 아님): 이전 계정이 남긴 로컬 행·사진 파일의 즉시 삭제(저장공간 회수), 서버 동기화 도입, 계정별 물리적 DB 파일 분리.

### 3. 요구사항

**필수 (P0)**
- `FilmRolls` 테이블에 계정 식별자 컬럼 추가 + Drift 스키마 마이그레이션(`schemaVersion` 1 → 2).
- `FilmRollLocalDataSource`의 모든 조회 메서드(`findAll`, `findById`, `findActiveByRegion`, `watchById`)가 현재 로그인 계정으로 필터링되어야 한다. `findById` 기반 직접 접근(예: `RecoverLastActiveFilmRollUseCase`)도 동일하게 보호되어야 한다.
- 필름롤 생성(`insert`) 시 현재 로그인 계정 식별자를 함께 저장.
- 로그인 성공 시(`login_screen.dart` `_handleLoginResponse`) 서버에서 현재 계정 식별자(`UsersApi.getMyInformation().id`)를 조회해 로컬에 저장.
- 로그아웃(`_onLogoutTap`)·회원탈퇴(`_onWithdrawTap`) 시 저장된 계정 식별자를 삭제.

**중요 (P1)**
- 스플래시 화면(`splash_screen.dart` `_runInitFlow`)에서 이미 인증된 세션으로 재개되는 경우(앱 재시작)에도 로컬 계정 식별자가 유효한지 보장 — 마이그레이션 직후 첫 실행처럼 값이 없는 케이스 처리.
- 계정 필터 값을 `FilmRollModule`/리포지토리 생성 시점에 캐싱하지 않고, 매 쿼리 시점에 다시 읽도록 설계 — 프로세스 내에서 로그아웃 후 다른 계정으로 즉시 로그인하는 경우에도 `FilmRollModule` 싱글턴을 재생성할 필요 없이 정확히 동작하게 한다.
- 마이그레이션 시점의 기존(계정 미표시) 로컬 행에 대한 backfill 정책 결정 및 문서화.

**선택 (P2)**
- 로그아웃 시 `AppPreferences`의 `last_active_film_roll_id`(`lib/core/config/app_preferences.dart:3,15-28`)도 함께 정리. 단, `RecoverLastActiveFilmRollUseCase`(`recover_last_active_film_roll_use_case.dart:18-30`)가 이미 "조회된 필름롤이 없거나 상태가 진행중이 아니면 저장값을 정리하고 null 반환"하는 자기 치유 로직을 갖고 있어, P0의 계정 필터링만 적용되어도 다른 계정 소유 id는 `findById`에서 자동으로 걸러져 안전하다. 따라서 이 항목은 필수가 아닌 위생 차원의 보완으로 분류한다.
- 타 계정 소유의 오래된 로컬 사진 파일/행 정리(저장공간 회수)는 별도 이슈로 분리 제안.

### 4. 선택한 접근 방식

**방식**: `film_rolls` 테이블에 계정 식별자 컬럼을 추가하고, 모든 로컬 조회/생성 경로를 현재 로그인 계정 기준으로 필터링한다(브레인스토밍 단계에서 사용자가 선택).

**이유**
- 이 앱은 필름롤 진행 데이터에 대한 서버 동기화가 아직 없다(`photos_table.dart:23-24`의 `isSynced` 필드는 "서버 동기화는 이번 스코프 밖"이라는 주석과 함께 예약만 되어 있음, `#41` 참고). 즉 로컬 DB가 유일한 원본이다. 로그아웃 시 전체 삭제 방식(MVP)을 택하면 아직 서버에 반영되지 않은 진행 중 데이터가 계정 전환 없이 단순 로그아웃만 해도 영구 손실될 위험이 있다.
- 계정별 물리 DB 파일 분리는 격리가 가장 완전하지만, `AppDatabase.instance` 단일 참조를 가정하는 코드(예: `my_screen.dart:109`의 `DriftDbViewer(AppDatabase.instance)`, `FilmRollModule` 전체)를 광범위하게 재검토해야 해 이번 버그 수정 범위 대비 과도하다.
- 컬럼 추가 + 필터링 방식은 기존 단일 파일/단일 싱글턴 구조를 유지하면서 계정 간 데이터 노출만 정확히 차단하고, 기존 데이터도 보존할 수 있어 위 두 대안보다 위험 대비 효과가 크다.

**대안**
- 로그아웃/계정전환 시 로컬 데이터 전체 삭제(MVP): 구현은 가장 단순하지만 위에서 설명한 데이터 유실 위험으로 기각.
- 계정별 DB 파일 분리: 격리는 가장 강력하지만 변경 범위가 크고 이번 이슈 대비 과설계로 판단해 기각.

### 5. 주요 결정사항

| 결정 | 선택 | 이유 |
|------|------|------|
| 계정 스코프 저장 위치 | `film_rolls` 테이블에 `userId` 컬럼 추가 (NOT NULL) | `film_roll_places`/`photos`는 `film_rolls`에 대한 FK cascade(`film_roll_places_table.dart:9-10`, `photos_table.dart:12-13,35-38`)로 이미 연결되어 있어, `film_rolls`만 스코핑하면 하위 테이블 조회도 `filmRollId` 경유로 자연히 계정 범위 안에 머문다. 별도 컬럼을 하위 테이블에도 중복 추가할 필요 없음 |
| 로그인 계정 식별자 소스 | 로그인 성공 직후 `UsersApi.getMyInformation()` 1회 호출 후 결과의 `id`를 로컬에 저장 | 서버 로그인 응답(`OAuthLoginResponse`)에 계정 id가 없고, JWT 클레임을 클라이언트에서 파싱하는 기존 패턴도 없음. 이미 검증된 `/api/users/me` 호출을 재사용하는 것이 가장 낮은 리스크 |
| 로컬 계정 식별자 저장소 | `AppPreferences`(SharedPreferences 래퍼, `app_preferences.dart`)에 동일 패턴으로 `currentUserId` 키 추가 | 토큰처럼 민감하지 않은 단순 값이며, 이미 이 프로젝트의 관례(`last_active_film_roll_id` 등)와 일치 |
| 필터 값 조회 시점 | `FilmRollModule`/리포지토리 생성자에서 캐싱하지 않고, 각 조회/생성 메서드 호출 시점에 `AppPreferences`에서 다시 읽음 | `FilmRollModule.instance`(`film_roll_module.dart:24-57`)는 로그아웃/로그인 시 재생성되지 않는 프로세스 전역 싱글턴이다. 생성 시점 캐싱은 같은 앱 세션 안에서 로그아웃 후 다른 계정으로 바로 로그인하는 시나리오(이슈 재현 절차와 동일)에서 값이 갱신되지 않는 문제를 재도입한다. 매 호출 조회 방식은 이미 async인 데이터소스 메서드에 자연스럽게 들어가며 싱글턴 재생성 로직을 새로 만들 필요가 없다 |
| 레거시(마이그레이션 이전) 행 backfill | 마이그레이션 실행 시점에 로그인되어 있는 계정의 id로 일괄 backfill | 기존 스키마는 계정 정보를 전혀 남기지 않아 사후 정확한 귀속이 불가능하다. 마이그레이션 시점의 로그인 계정으로 배정하는 것이 실용적 최선이며, 리스크는 아래 "고려사항" 참고 |
| `last_active_film_roll_id` 처리 | 로그아웃 시 명시적으로 초기화(P2) | 없어도 `RecoverLastActiveFilmRollUseCase`의 기존 자기 치유 로직으로 안전하지만, 위생적 정리를 위해 함께 처리 권장 |

### 6. 고려사항 및 위험요소

**기술적 위험**
- **레거시 데이터 backfill 부정확성**: 마이그레이션 시점에 로그인된 계정으로 기존 미표시 행을 일괄 배정하므로, 이미 이 버그로 인해 한 기기에 두 계정의 데이터가 뒤섞여 있던 사용자는 배정이 완벽하지 않을 수 있다(일부 다른 계정 소유 행이 마이그레이션 시점 로그인 계정 소유로 잘못 라벨링될 수 있음). 스키마가 계정 정보를 원래 남기지 않았으므로 사후 완전 복구는 불가능 — 이번 수정 이후 신규 생성 데이터부터는 정확히 격리됨을 목표로 한다.
- **저장공간 누적**: 필터링만 적용하고 삭제하지 않으므로, 이전 계정이 만든 사진 파일/행은 기기에 계속 남아 저장공간을 차지한다(사용자가 이번 스코프에서 명시적으로 수용한 트레이드오프). 후속 이슈로 정리 작업 제안.
- **필터 누락 지점 재발 위험**: 향후 `FilmRollLocalDataSource`/`FilmRollPlaceLocalDataSource`/`PhotoLocalDataSource`에 새 조회 메서드가 추가될 때 계정 필터를 빠뜨리면 동일 버그가 재발할 수 있다. 코드 리뷰 체크리스트 또는 테스트로 보완 필요.

**비즈니스 위험**
- 없음 (오프라인 전용 데이터 격리 문제로, 서버/과금/외부 연동 영향 없음).

### 7. 성공 기준

- [ ] 카카오 계정으로 로그인 후 필름롤 생성 → 로그아웃 → 구글 계정 로그인 시 필름롤 목록 화면에 카카오 계정의 필름롤이 보이지 않는다.
- [ ] 위 재현 절차를 앱을 완전히 종료했다가 재실행하는 경우와, 앱을 종료하지 않고 연속으로 수행하는 경우 모두에서 성립한다.
- [ ] 구글 계정으로 다시 로그아웃 후 카카오 계정으로 재로그인하면, 카카오 계정 본인의 기존 필름롤이 정상적으로 다시 보인다(단순 삭제가 아니라 계정별 격리임을 검증).
- [ ] `RecoverLastActiveFilmRollUseCase`가 다른 계정의 필름롤 id를 가리키는 경우 정상적으로 null을 반환하고 저장값을 정리한다.
- [ ] 마이그레이션 실행 후 기존 사용자의 앱이 크래시 없이 기동되고, 로그인 중이던 계정 기준으로 기존 필름롤이 계속 보인다.
